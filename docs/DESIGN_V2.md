## 1. AI-Trader (HKUDS): что это по существу
### 1.1 Что подтверждается источниками
- Проект группы HKUDS (университет Гонконга). ~22-23 тыс. звёзд, ~3.4 тыс. форков, Python, последнее обновление в выдаче 2026-06-11 [С]. Есть две ипостаси: (а) научный бенчмарк «AI-Trader: Benchmarking Autonomous Agents in Real-Time Financial Markets» (arXiv 2512.10971): окружение живой торговли и агенты развязаны, MCP-инструменты, данные, промпты; рынок: акции NASDAQ-100 и крипта, заявленный капитал симуляции $10 000 / 100 000 CNY [С]; (б) «AI-Trader 2.0»: платформа «agent-native trading» на ai4trade.ai.
- Архитектура платформы: FastAPI-бэкенд (`service/server`), React/Vite фронтенд, отдельный фоновый воркер [С].
- Подключение агентов: агент читает `SKILL.md` по ссылке с ai4trade.ai и сам регистрируется через REST; главный SKILL.md это роутер на «дочерние» скиллы (copytrade, tradesync, heartbeat, Polymarket, market intelligence). Заявлена совместимость с Claude Code, Codex, Cursor, OpenClaw, nanobot. «Токен это ваша личность» (цитата из SKILL.md, переданная обзором) [С].
- Сигналы трёх типов: strategies (обсуждение), operations (для копирования), discussions (коллаборация) [С]. Есть копитрейдинг и «следование», торговля бумажная (в README: Polymarket paper trading с реальными данными и симулированным исполнением), очки (100 приветственных), челленджи и награды, покупка сигналов [С].
- Реальная торговля на биржах: **в найденных источниках не подтверждена**; везде описана симуляция/бумага и синхронизация позиций «между брокерами» (tradesync, без названий) [С/Н].

### 1.2 Маркетинг против подтверждённого
| Заявление | Оценка |
|---|---|
| «100% fully-automated», «agent-native» | По сути это REST + файлы-инструкции для LLM-агентов; «автоматизация» целиком зависит от внешнего агента. Бирже ордера не отправляются (по найденному). |
| Доходность/бэктесты | В найденных источниках нет проверяемых цифр; бенчмарк это сравнение моделей в симуляции, не доказательство edge. Не использовать как довод. |
| Маркетплейс сигналов/копитрейдинг | Это социальный слой поверх бумажных счетов и очков. Репутация измеряется на симуляции, где нет проскальзывания и комиссий реальных денег [Н]. |

### 1.3 Безопасность и «текст для агентов»
- Модель «агент читает SKILL.md с чужого сайта и выполняет» это канал prompt injection по построению: владелец ai4trade.ai (или тот, кто взломает сайт/зависимость) получает право давать инструкции вашему агенту. Для нас это красная линия: **внешние SKILL.md в торгового агента не подключать**. Инструкции в SKILL.md/README (регистрация, «сохрани токен», подгрузи дочерние скиллы) здесь отмечены и **не выполнялись**.
- Данные: регистрация, токен, публикуемые сигналы и (в tradesync) позиции уходят на сервис третьей стороны. Для реальных денег это раскрытие стратегии/позиций. Ключей биржи сервис, по описанию, не требует [Н].
- Лицензия: MIT по одному вторичному источнику, по другому неясно [Н]. Идеи заимствовать можно свободно (идеи не защищены), код копировать только после чтения LICENSE.

### 1.4 Что применимо нам, что нет
Применимо (идеи, не код):
1. **Контракт «сообщение сигнала»**: типизированные записи (strategy/operation/discussion). Нам нужна лишь локальная версия: `signal` (кто, символ, сторона, уровни, срок жизни, обоснование) в общем журнале событий.
2. **Бумажный счёт на каждого агента** и сравнение агентов по одинаковой метрике: это ровно то, чего нам не хватает, чтобы проверять гипотезы без риска денег (у нас уже есть `ideas` + `hot_outcomes`).
3. **Skill-файлы как интерфейс**: короткий локальный `skills/<agent>.md` с контрактом (какие команды `./tb` разрешены, формат сообщений). Но только локальные, написанные нами.
4. **Heartbeat**: периодический «я жив» агентов. У нас аналог `runtime/health.json`.
5. Бенчмарк-подход (arXiv): развязка «окружение» и «агент», одинаковые данные для всех.

Не применимо:
- Публичный маркетплейс/копитрейдинг, очки, соцсеть: у нас один владелец и ~39 USDT; чужие сигналы это недоверенные данные и чужая задержка.
- Облачная платформа и общий токен-идентификатор: лишняя поверхность атаки.
- Бумажная репутация как доказательство edge: у нас при n<30 выводов не делаем (`TRADING.md`).
- Тяжёлый стек (FastAPI+React+worker+БД): противоречит правилу «только stdlib, кроссплатформенно».

Вывод: AI-Trader полезен как **каталог идей** (контракт сигнала, бумажный счёт на агента, heartbeat), а не как зависимость. Подключаться к нему не рекомендую.

## 2. Наш текущий дизайн
### 2.1 Сильные стороны [В, по docs/код]
- Детерминированный риск-слой `core/guard.py` + профиль `config/risk_profile.json`: размер/плечо считает код, а не LLM; стоп и тейк встроены в ордер (атомарно, в т. ч. лимитные входы); лестница просадки, дневной лимит, корреляционные группы, сессии с бюджетом.
- Журнал только дописывается (`state/trades.jsonl`), есть `ctx`, MAE/MFE, теги ошибок; идеи и статистика пропущенного; сканер всего рынка с антиспамом (экономия токенов: просыпаемся по событиям, не по таймеру).
- Файловая шина (`runtime/*.json`, `events.jsonl`), атомарная запись (`fsutil.replace`), файловые блокировки в `pending.py`, дашборд только на чтение, stdlib, 466+ тестов, кроссплатформенность.
- Ключи Bybit подгружаются обёрткой в окружение процесса; клиент с белым списком методов, вывода/перевода нет.

### 2.2 Узкие места
| # | Проблема | Следствие |
|---|---|---|
| 1 | Мозг живёт только внутри интерактивной сессии Claude Code; Monitor/cron не переживают смену чата | Позиции защищены биржевыми стопами, но реакция на события (sl_hit -> sync -> разбор, идея достигла уровня) пропадает, пока чат закрыт |
| 2 | Каждое пробуждение тащит весь контекст чата (десятки тыс. токенов) | Дорого по лимиту подписки, раздувается контекст, растёт шанс ошибок |
| 3 | Нет очереди задач и подтверждений: события идут в stdout Monitor-а, при перезапуске теряются (`watch` это признаёт) | Нет «at-least-once», нет аудита «кто что обработал» |
| 4 | Нет разделения ролей: один агент-человек-в-цикле сканирует, решает, исполняет, разбирает | Нет независимой проверки; ошибка рассуждения доходит до ордера (защищает только guard) |
| 5 | Исполнение и ключ торговли доступны той же среде, где работает LLM (через `./tb bybit trade`, права в `PERMISSIONS.md`) | Guard вызывается тем же процессом; обход технически возможен (ручной вызов клиента) |
| 6 | Состояние в файлах без единого процесса-владельца | Работает благодаря локам, но нет единого «источника правды» об открытых позициях и заявках |
| 7 | Дашборд только чтение, уведомлений нет | Владелец узнаёт о событии, только открыв экран |
| 8 | Edge не найден (`RESEARCH.md`): ценность системы сейчас в дисциплине риска и сборе данных | Любое усложнение должно окупаться безопасностью/наблюдаемостью, не «ростом доходности» |

## 3. Целевая архитектура v2
Принцип: **LLM никогда не получает ключ и не вызывает биржу; он может только отправлять «намерения» в детерминированный контур, который их проверяет и исполняет.**

### 3.1 Роли
| Роль | Что делает | LLM? | Права |
|---|---|---|---|
| Сканер (есть: hotscan, feed, ideawatch) | события рынка, идеи с уровнем | нет | чтение публичных данных |
| Триажёр | отсеивает события, формирует «досье» из 5-15 строк, будит аналитика только при `score`/идее | дешёвая модель или правила | чтение runtime, запись `signal`/`wake` |
| Аналитик гипотез | тезис, уровни, `intent` (вход/выход/отмена) | сильная модель | чтение; запись только `intent` в очередь |
| Риск-контур + Исполнитель (`tbd-exec`, отдельный процесс) | проверяет `intent` через guard, исполняет, ведёт ждущие лимиты, sync, журнал | **нет** | единственный держатель ключа trade |
| Ревьюер/постмортем | разбор закрытых сделок, теги, уроки, `journal post` | модель по расписанию/событию close | запись в разборы, не в ордера |
| Исследователь | офлайн-гипотезы на `data/`, предрегистрация | модель, вручную | чтение данных, запись в `research/` |
Мультиагентность здесь логическая (роли = разные промпты/точки входа), а не десять процессов; физически: сканер(ы), исполнитель, один оркестратор вызовов LLM, дашборд.

### 3.2 Шина событий и очередь (без тяжёлых зависимостей)
- **Каталог-очередь на файлах** `state/bus/`: `events.jsonl` (append-only, монотонный `seq`, `type`, `ts`, `src`, `payload`), `intents/` (по файлу на намерение, атомарная запись tmp+rename), `acks.jsonl` (кто обработал `seq`). Плюс курсор потребителя `runtime/cursors/<agent>.json`: даёт at-least-once, переживает рестарты, не требует брокера.
- Локальный HTTP (http.server, 127.0.0.1, токен в заголовке) нужен только если агенты окажутся в разных песочницах/машинах; на старте избегать. Redis/NATS/SQLite-сервер не нужны. SQLite (stdlib `sqlite3`) допустим как замена индексам файлов, если число событий вырастет; обоснованная точка перехода: >100 тыс. записей или нужны запросы по состояниям.
- Идемпотентность: у `intent` обязательный `intent_id` (UUID), исполнитель отвечает по нему один раз (результат в `intents/<id>.result.json`); повтор не создаёт второй ордер. `orderLinkId` у нас для этого уже используется.

### 3.3 Контракт сообщений (интерфейс для новых агентов)
```
signal  {schema:1, id, agent, ts, sym, side, thesis, level, stop, tp, ttl_min, confidence, evidence:[...]}
intent  {schema:1, intent_id, agent, ts, action: open|close|cancel|set_stop_tighter, sym, side?, order:{type, price?, sl, tp}, idea_id?, session_id, thesis, expires_ts}
result  {intent_id, status: accepted|rejected|executed|failed, guard:{ok,reasons,leverage,margin}, journal_id?, error?}
```
- Агент не передаёт размер/плечо/маржу: их считает guard (как сейчас). Поля, которых нет в схеме, отбрасываются; строки очищаются (длина, управляющие символы) - защита от injection через `thesis`.
- Права по агенту (`config/agents.json`): какие `action`, какие символы, дневной лимит `intent`-ов, максимум открытых от этого агента, режим `paper|live`. Новый агент по умолчанию `paper`: его intent исполняется на бумажном счёте (журнал `mode=paper`, уже поддерживается дашбордом), в live только после решения владельца.
- «Песочница»: агент работает в отдельном процессе без env-ключей, у него есть только запись в `bus/intents` и чтение `runtime`. Для Claude Code-сессии это согласуется с текущими разрешениями (`PERMISSIONS.md`): убрать из allow-листа прямой `./tb bybit trade open`, оставить `./tb intent submit`.

### 3.4 Единый риск-контур
- `tbd-exec`: долгоживущий процесс (или короткий запуск по событию) с ключом trade, единственный, кто вызывает `venues/bybit.py` на запись. Внутри: `guard.evaluate` как библиотека, ПЛЮС жёсткие лимиты, которые не читаются из изменяемых агентом файлов: `config/risk_profile.json` права на запись только у владельца (ОС-права/ACL), хеш профиля проверяется и пишется в журнал; изменение лимитов = подтверждение владельцем (2 шага: файл + `./tb limits confirm`).
- Ключи: trade-ключ в `~/.config/traider-bot/` с правами 600, читает только пользователь, под которым запущен `tbd-exec`; у LLM-процессов (агентов) другого ОС-пользователя или хотя бы без доступа к каталогу. Ключ Bybit без права вывода, привязка к IP (как сейчас).
- Аварийный выключатель: файл `state/KILL` (создаёт владелец или дашборд) -> исполнитель отвергает все новые `open`, при флаге `flatten` закрывает позиции. Стопы на бирже остаются защитой при падении демона.
- Сверка: раз в N секунд `positions`/`orders` на бирже против журнала; расхождение -> событие `reconcile_alert`, запрет новых входов.

### 3.5 Хранение состояния
Остаются файлы (журнал jsonl, portfolio.json, pending_orders.json с локом). Новое: `state/bus/*`. Единственный писатель каждого файла = один процесс (исполнитель пишет trades/pending/portfolio; сканер пишет runtime). Это снимает гонки без БД.

### 3.6 Наблюдаемость
- Дашборд: вкладка «Агенты» (очередь, intent -> result, отказы guard с причиной, расход токенов и $ по ролям, последний heartbeat), баннер «KILL активен».
- Аудит: `state/audit.jsonl` (кто, какой intent, какие проверки, хеш профиля, версия кода). Уведомления: push на телефон (ntfy/Telegram бот только на исходящие, без команд на вход) для fills, sl/tp, reconcile_alert, превышения бюджета API.

### 3.7 Миграция по шагам (без остановки торговли, совместимость журнала и CLI)
- Журнал `trades.jsonl` не меняется (только дописывание, новые необязательные поля `agent`, `intent_id`). CLI `./tb ...` сохраняется: `./tb bybit trade open` становится тонкой обёрткой, которая вместо прямого вызова кладёт intent и ждёт result (флаг `--direct` остаётся для владельца).
- Переиспользуем без изменений: `core/*`, `venues/*`, `marketdata/*`, `dash/*`, `launcher.py`, `paths.py`, тесты. Пишем заново: `core/bus.py` (очередь/курсоры), `core/intents.py` (схема, санитизация), `tools/exec_daemon.py`, `core/agents_cfg.py`, `llm/runner.py` (вызов Claude), вкладка дашборда. Переписывать guard и журнал не нужно.

## 4. Режимы интеграции Claude
### 4.1 Цены (из справочника Claude API на 2026-10-06; проверить на pricing)

| Claude Opus 5.5 | 4 | 20 | 0.20 |
| Claude Sonnet 5.5 | 2 | 10 | 0.20 |
| Claude Haiku 5.5 | 0.10 (до 100K контекста) | 0.50 | н/д [Н: ~0.01] |

### 4.2 Допущения расчёта
Один «триажный» вызов: вход 3k, выход 0.2k (Haiku). Один «решающий» вызов с инструментами: кэшируемый префикс (система+инструменты+регламент) 6k, свежий вход 2k на шаг, в среднем 4 шага, выход 1k суммарно с рассуждением на шаг (≈0.6-1.5k). Сильная модель вызывается на ~10% пробуждений.
Стоимость решающего вызова (4 шага, префикс в кэше на 2-4 шага, остальное промах):
- Opus 5.5: ≈ $0.12-0.30; Sonnet 5.5: ≈ $0.05-0.15; Fable 5.1: ≈ $0.30-0.75 [Н, грубо].
Месяц = 30 дней.

### 4.3 Сравнение режимов
| | A. Сессия Claude Code + Monitor (как сейчас) | B. Демон + Messages API (или Agent SDK) | C. Гибрид: Haiku/Sonnet триаж + Opus/Fable решение |
|---|---|---|---|
| Работает без открытого чата | нет | да | да |
| Стоимость в $ (оценка) | 0 маргинально, но жжёт лимиты подписки; фактический лимит не проверен [Н] | 100 пробуждений/день все на Sonnet 5.5 ≈ $45-90/мес; все на Opus 5.5 ≈ $120-250/мес; Fable 5.1 ≈ $300-600 | Haiku на 150 событий/день ≈ $2/мес + ~10 решений/день: Sonnet ≈ $15-45, Opus ≈ $35-90 => **итого ≈ $20-100/мес** |
| Задержка | секунды, но нужен живой чат | 2-30 с на вызов (Opus/Fable дольше при рассуждении) | триаж <2 с, решение 5-60 с; приемлемо для scalp не годится при любом LLM |
| Безопасность | ключ в окружении процесса, который запускает `./tb`; LLM рядом с ключом | ключ Anthropic в env демона, ключ Bybit только у `tbd-exec`; чёткое разделение | то же, что B; триаж не имеет права на intent |
| Управляемость | ручная, видна в чате | бюджет токенов на сутки, лимит вызовов, кнопка KILL, лог каждого вызова | то же + разные модели по роли |
| Подтверждение лимитов человеком | неявное (чат) | лимиты вне LLM, изменение профиля только владельцем | то же |
| Сложность | 0 | средняя (цикл tool-use, кэш, ретраи, учёт $) | средняя+ (маршрутизация) |
Примечание про Agent SDK: это Claude Code как библиотека (готовый цикл, файловые и bash-инструменты, хуки, разрешения). Подходит, если нужны готовые инструменты, но тащит больший контекст на вызов и широкие встроенные права (bash). Для узкого контура торговли надёжнее **Messages API с 4-6 собственными инструментами** (read_state, submit_intent, journal_note, wait). Вариант A' (дёшево): запускать `claude -p` по событиям из демона на подписке; условия подписки для автоматического запуска и лимиты **не проверялись** [Н].

### 4.4 Безопасность ключей и аудит в режимах B/C
- Ключ Anthropic: отдельный workspace/ключ с лимитом расходов в консоли (spend limit), в env демона `llm-runner`, не в репозитории, не в `state/`. Ключ Bybit trade: только у `tbd-exec`.
- LLM-процесс не имеет сетевого доступа к Bybit и файла ключей (отдельный ОС-пользователь или хотя бы отдельная учётка с chmod 600).
- Аудит: каждый вызов LLM пишется в `state/llm_calls.jsonl` (модель, токены вход/выход/кэш, $, `seq` события, id результата). Дневной потолок расходов -> при превышении деградация до «только Haiku/правила» и уведомление.
- Сторонний текст (названия монет, новости, README) подаётся в промпт только как данные в разделителях, с санитизацией; ответ LLM принимается только в виде tool_use по схеме (strict), свободный текст не исполняется.

### 4.5 Точка безубыточности
Окупаемость API: `капитал × чистая_месячная_доходность ≥ стоимость_API`.
- Капитал 39 USDT: даже самый дешёвый вариант C на Sonnet ($20/мес) требует 51% в месяц; $100/мес — 256%. Нереалистично.
- При реалистичной **оптимистичной** чистой доходности 5%/мес (edge не доказан, возможно 0 или минус): C за $20/мес окупается при капитале ≥ **$400**; за $60 — ≥ **$1200**; за $100 — ≥ **$2000**. При 10%/мес вдвое меньше ($200 / $600 / $1000).
- Минимальный чисто «инфраструктурный» вариант (только Haiku, триаж и разбор, без решающей сильной модели): ≈ $2-5/мес, окупается при капитале ≥ $50-100 и 5%/мес, т. е. около текущего счёта, но выгоды в прибыли не даёт, только в надёжности.
- Вывод: **деньги на API должны оправдываться надёжностью/дисциплиной, не прибылью**, пока счёт < ~$500 и нет доказанного edge. При подписке Claude Code режим A «бесплатен» маргинально.

## 5. Риски и «чего НЕ делать»
- **Ордера из двух мест / гонки**: ни один агент не пишет в `trades.jsonl`, `pending_orders.json`, `portfolio.json`, кроме исполнителя; прямой `bybit trade` в allow-листе агента убрать после этапа 2. Один символ = один открытый intent.
- **LLM мимо риск-контура**: любой путь к бирже только через `tbd-exec`; ключ у LLM-среды отсутствует; guard не импортируется агентом как «совет», а применяется исполнителем.
- **Prompt injection через данные**: названия тикеров, новости, README/SKILL.md внешних проектов (включая AI-Trader) = недоверенный текст; никогда не подключать чужие skill-файлы; схема intent строгая; нет инструмента «выполнить команду»/«прочитать ключ»; нет произвольного URL-fetch в торговом агенте.
- **Раздувание сложности**: не вводить брокер сообщений, БД-сервер, веб-фреймворк, контейнеры. Каждое добавление должно закрывать конкретное узкое место из 2.2.
- **Честный ответ про мультиагентность**: при 39 USDT, одном владельце и отсутствии edge полноценная мультиагентность **не нужна**. Нужны (1) исполнение вне LLM, (2) работа без открытого чата, (3) дешёвый триаж, (4) ревью/постмортем. Всё остальное — позже и только при росте капитала.

## 6. Рекомендация и этапы
**Рекомендация: C-light, поэтапно. Сначала детерминированная автоматика без LLM (шаги 1-2), потом интент-слой (3), и только затем LLM-демон (B/C) на Haiku + Sonnet, Opus/Fable по запросу. Не подключаться к AI-Trader.**

### Этап 0 (ничего не ломая, ~1 день)
- Что: схемы `signal/intent/result` как документ + тесты на схему; `config/agents.json` (пока один агент `claude-session`); метрика расхода: считать число пробуждений сканера/день (`hot_events.jsonl`).
- Готово: схемы и тесты зелёные, ни одна строка живого пути не изменена. Откат: удалить новые файлы.

### Этап 1 (автоматика без LLM, ~3-4 дня)
- Что: `core/bus.py` (события+курсоры), демон `tbd-exec` в режиме «только sync»: реагирует на `sl_hit/tp_hit/fill/ws_down`, делает `sync`, снимает pending, шлёт push; reconcile; файл KILL.
- Готово: 7 дней подряд позиции/заявки сверяются без участия чата; после искусственного рестарта демона события не теряются (тест); нет двойных записей в журнале. Откат: остановить демон, вернуться к cron sync раз в 15 минут (остаётся как запасной).

### Этап 2 (интенты и LLM, ~1-2 недели)
- Что: `./tb intent submit`, исполнитель принимает open/close/cancel с guard; trade-ключ только у исполнителя; `llm/runner.py` на Messages API: Haiku-триаж + Sonnet 5.5 для решений, Opus 5.5 только для разбора/спорных; кэш префикса, учёт $, потолок в день; режим `paper` по умолчанию для нового агента.
- Готово: 14 дней без обходов контура (аудит), средний расход ≤ согласованного бюджета, сравнение «решение демона vs сессия» на бумаге не хуже по дисциплине (доля нарушений правил), тесты контракта. Откат: переключатель `mode: session` (вернуть прямой `bybit trade`, права назад), демон выключен.

### Что требует решения владельца
1. Бюджет на API (рекомендация: не больше $5-10/мес при капитале < $200; расходы выше — только при росте капитала по формуле 4.5).
2. Создание отдельного ключа Anthropic со spend limit; где его хранить.
3. Разделение ОС-пользователей/прав на каталог с ключом Bybit; согласие убрать прямой `bybit trade` из allow-листа после этапа 2.
4. Канал уведомлений (ntfy/Telegram: только исходящие).
5. Любые изменения лимитов (остаются за владельцем и подтверждаются вне LLM).
6. Согласие/запрет на регистрацию на внешних платформах (AI-Trader): рекомендую запрет.
