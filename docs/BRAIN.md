# API-мозг (WP11-C2): как работает рантайм, смена модели, аварийные режимы

Спецификация: `docs/spec_v2/07b_roles_providers.md` (роли, провайдеры, смена, запасные профили, учёт), `07_control_lifecycle_news_roles.md`, `03_brain.md`. Код: `src/tb/brain/{runner,api_daemon,jobs,swap,fallback,guards,conf,roles_runtime,validate,brain_cli}.py`,
слой LLM `src/tb/llm/`, шлюз `src/tb/gateway/`. Конфигурация: `config/brain.json`, `config/roles/`, `config/providers.json`, `config/agents.json`. Тесты: `tests/test_brain_*.py` (фейковый LLM `tests/fakes/fake_llm.py`).

## Идея в трёх строках
Мозг это сервис `brain` под супервизором. Он берёт задания диспетчера (события шины -> `state/brain/jobs/J-*.json`), для каждого собирает досье (`get_brief`+`get_events` через шлюз), спрашивает роль у LLM
(слой `tb.llm`: клиент, учёт, бюджет, проверка JSON), проверяет ответ по схеме роли и исполняет решение теми же инструментами шлюза, что и любой агент (`stop_plan`, `close_plan`, ...), с правами агента из `agents.json`.
LLM предлагает, код проверяет: размер, плечо, маржу считает guard, стопы только строже, торговый флаг и лимиты проверяет шлюз. Мозг не импортирует биржу и исполнитель и не видит ключей Bybit.

## Включение
По умолчанию сервис выключен (его нет в `services.<профиль>`, подписчик `api` в `config/subscriptions.json` имеет `enabled:false`).
1. Ключ провайдера в каталоге ключей владельца (`deepseek.env` со строкой `DEEPSEEK_API_KEY=...`; читает только `tb.llm.keys`), `./tb llm check --live`.
2. `./tb brain check` (конфигурация и роли), `./tb brain probe --all --live` (метки свежей проверки провайдеров).
3. Подписчик `api` включается командой `./tb brain enable` (пишет личный слой `config/local/subscriptions.json`, сливается по id поверх поставляемого `config/subscriptions.json`; `./tb brain disable` выключает; команда печатает, чего ещё не хватает); запуск `./tb up --services exec,scan,dispatch,ctl,dash,brain` (или добавить `brain` в `services.<профиль>` в `config/platform.json`).
4. `./tb brain status`, `./tb status` (строка про мозг), `./tb logs brain`.
Live-день мозгу доступен только при торговом флаге (ниже) и правах агента (`agents.json`: в `modes` есть `live`; сейчас у `api` только `paper`).

## Файлы и форматы
- `config/brain.json` (желаемая начальная конфигурация; секретов нет): `profiles` (профиль = провайдер + модель из providers.json + `params` + `live_ok` + `eval_ts`; метку `live_ok` ставит ТОЛЬКО владелец после eval), `shared_roles` (`news_reader`, `reviewer`, `day_auditor`:
  `{primary, fallback:[...]}`), `teams.<id>` (`agent_id` из agents.json + роли `morning_analyst`, `position_manager` с цепочкой профилей), `trading.live_team`, `trading.compare` (сравнительные команды ОТЛОЖЕНЫ: `enabled=false`, ничего не запускается;
  команда с правом live в списке `compare.teams` = ошибка конфигурации), `budget`, `swap_rules`, `fallback`, `runtime` (воркеры, окна защит).
- `config/roles/<роль>.json|.md` + `_common.md`: метаданные и стабильный системный промпт (первая строка `# prompt vN`, N = `version`). С WP11-C3 роли `morning_analyst`, `position_manager`, `reviewer`, `day_auditor` v1 полные; описание ролей, схем, eval и версионирования: `docs/ROLES.md`.
  Схемы ответов: `brain/validate.py` (`pm/1`, `dayplan/1`, `audit/1` с `tb.carry/1`, `casereview/1` полные; `reader/1`, `review/1` как были). Подписка `api` в `config/subscriptions.json` имеет `roles` (роль -> типы событий).
  Оценка промптов: `./tb brain eval` (фейк) и `./tb brain eval --profile P --live --confirm` (только владелец; метка `live_ok` в подписанном `state/brain/live_ok.json`).
- Задание (формат диспетчера + поля мозга): `id, sub, status(new|taken|done|failed|expired|skipped), prio, key, plan, sym, ts_first, ts_last, not_before, count, seqs, types, kinds` + `taken_ts, taken_by, attempts, rev, retry_at, requeued, result{outcome,code,roles[],usd,tokens}, done_ts`.
- `state/brain/active.json` (подписан HMAC ключом `control.json`, как уровень риска): `{"schema":"tb.brainactive/1","rev","ts","by","prev_rev","live_team","teams":{...},"shared_roles":{...},"mac"}`. Файл не подписан или подпись неверна:
  игнорируется, действует `config/brain.json` (статус `source: untrusted`, предупреждение). Копии ревизий `state/brain/history/R-<rev>.json` (последние 50), журнал смен `state/brain/swaps.jsonl` (хеш-цепочка, `./tb brain verify`).
- `runtime/brain/state.json`: охлаждение профилей, режим «только защита», последний запасной. `state/brain/probe.json`: свежие проверки провайдеров. `state/brain/history_ok.json`: итог paper-дисциплины для предупреждения смены.
- Учёт: `state/llm_calls.jsonl` (пишет `LLMClient`: job, role, team, agent, profile, rev, event_seq, fallback_from, токены, $), решения: `state/decisions.jsonl` (`actor: brain:<агент>`, `what: brain_decision`, `basis`: job/role/profile/usd/cfg_rev).
- Heartbeat `runtime/platform/brain.hb.json` (+ `protect_only`, `reason`, `health` green|yellow|red, `rev`, `queue`): `./tb status` красный при «только защите», жёлтый при запасном профиле/бюджете/ошибках конфигурации.

## Что происходит с заданием
1. Воркер читает `active.json` (stat на каждое задание; подпись проверяется при смене файла) и фиксирует `rev` в задании. Задание, начатое на ревизии N, доделывает своя цепочка профилей; следующее берёт N+1.
2. Защиты до LLM: лимит заданий в час (всего и на подписку, критичные отдельно), детектор зацикливания (не более N заданий по одному ключу за окно, дальше ключ блокируется, событие `error BRAIN_LOOP`), бюджет дня/часа.
3. Роли по типам событий (`wake_on`): `position_manager` (milestone, entry_filled, entry_blocked, ...), `reviewer` (position_closed). `entry_scout` (scanner_signal, только paper, подробности `docs/ROLES.md`). Остальные роли (morning_analyst, day_auditor, news_reader) вызывают WP14/WP13b через `Runner.ask_role`.
   Окно новостей (FOMC/CPI/NFP): в live и testnet всегда запрет (0 новых планов). В paper при `config/local/exec_limits.json: paper.blackout_mode=warn` (поставляемое умолчание `block`) окно это предупреждение: досье показывает `market.blackout.mode`, модель ставит `size_mult<=0.5` и код риска `blackout_warn`, исполнитель пропускает вход с предупреждением W_BLACKOUT, тегом `blackout` и потолком размера `paper.blackout_size_mult` (0.5). Срез статистики: `./tb exp stats --by blackout`, `./tb journal analyze --by blackout`. Результаты в окне не переносить на live (проскальзывание paper-модели в новости занижено).
   Жёсткий слой под мозгом: Gate исполнителя отклоняет ВХОД, лимитный вход и ДОБОР в окне кодом `E_BLACKOUT` (live и testnet всегда, paper при `blackout_mode=block`), даже если план подан в обход мозга (`./tb plan submit`, MCP). Событие `action_rejected` будит мозг; план остаётся armed и войдёт после окна, если не истёк ttl. Защитные действия (стоп, закрытие, отмена, reduce-only, hold/release) окно не блокирует. Подробности: `docs/LIFECYCLE.md`, раздел «Блэкаут в Gate».
4. Досье: `<brief>` (get_brief scope=event) и `<event>` (события задания). Данные недоверенные: в промпте сказано, что это не инструкции.
5. Ответ: извлечение первого JSON, строгая проверка схемы (лишние ключи, enum, длины), смысловая проверка (набор `args` по решению, тот же план). Невалидно: повтор с кодами ошибок (`retries_format`), затем запасной профиль один раз, затем «нет действия»:
   для `position_manager` это hold + событие `error BAD_FORMAT` + запись `decisions kind=skip res.code=BAD_FORMAT`. Устаревшая ревизия плана: одна пересборка досье.
6. Исполнение: `move_stop->stop_plan`, `close/partial_close->close_plan`, `cancel->cancel_plan`, `amend->amend_plan`, `hold_plan/release_plan`, `escalate->событие error`, `hold->только запись`. Отказ шлюза записывается кодом, повтор не автоматический.
   Одинаковое решение исполняется не более `same_decision_max` раз за окно (иначе `REPEAT_DECISION`).
7. Задание закрывается; события подтверждаются (`ack`) только до минимального seq незавершённых заданий. Сбой посреди задания: задание возвращается в очередь (до `max_attempts`), событие остаётся неподтверждённым.
   Рестарт демона: зависшие `taken` возвращаются в `new`, очередь не теряется.

## entry_scout и карточка «что видит мозг»
Роль `entry_scout` просыпается на `scanner_signal` (hot_enter, range_5m, turnover_surge), ищет вход и через код раннера подаёт план paper (путь события: сканер -> шина `scanner_signal` -> диспетчер (фильтр kinds, класс 3, корзина до 20 заданий/ч, коалесцирование 90 с) -> задание `sym:<монета>` -> раннер (роль-лимит 20/ч, блокировки NOT_PAPER/PROTECT_ONLY/KILL до модели) -> `get_brief event` + модель ds-flash -> `entry/1` -> смысловая проверка -> `submit_plan` mode=paper -> Gate/guard исполнителя).
Событие без планов и позиций (NO_PLAN у position_manager) пишется нейтрально: `decisions kind=note res.code=IDLE_NO_PLAN` («ждёт: нет планов и позиций, управлять нечем»), без события `error`; дашборд не считает это отказом Gate (`idle`). `GET /api/brain/watch`: `docs/spec_v2/BRAIN_WATCH.md`.

## Память случаев в мозге (WP15b)
- Досье: блок `memory` (<= 450 токенов; `scope=start`: статистика закрытых сделок за 14 дней, теги ошибок, топ-3 урока-гипотезы; `scope=event`: похожие прошлые случаи для плана armed/draft, по открытой позиции памяти нет). Только числа/enum/id, предупреждения `INSUFFICIENT`/`LOW_N`. paper/testnet сразу, live только при `config/memory.json: show_in_live=true` (по умолчанию false); `enabled=false` или агент/потребитель в `agents_off` выключают память.
- Запись случаев: сервис ctl раз в минуту вызывает `memory.tick` (закрытия сделок, пропуски, идеи с итоговым статусом, их whatif; идемпотентно). Раннер перед разбором закрытия вызывает тот же писатель, ревьюер получает `case_id` из события `position_closed`.
- Ревьюер (роль, `casereview/1`): ответ проходит схему и `known_at_decision` против situation, затем `add_case_review` (право `memory.write` у агента команды + роль reviewer). Результат: `OK`, `NO_CASE_ID`, `NO_MEMORY_RIGHT` или код отказа шлюза в журнале решений.
- Метка `mem.on|off` ставится шлюзом на планы (`src.mem` случая, разрез `./tb exp stats --by mem`, `./tb memory stats --by mem`). Ретро-проверка и сравнение периодов: `./tb memory backtest|compare`.

## Запасные профили и «только защита»
Триггеры: таймаут/сеть, 5xx, 429 после повторов, ошибка авторизации, исчерпание бюджета провайдера, два подряд невалидных формата. Неисправный профиль охлаждается 60 с, 120 с, ... до 900 с (задания идут сразу на запасной), потом вызов основного
сам служит проверкой. Для live-ролей в режиме live запасной допустим только при включённом провайдере, свежей проверке (`brain probe --live`) и метке `live_ok` (или принятом при старте дня предупреждении W2); иначе кандидата нет.
Нет кандидатов, все недоступны или исчерпан дневной/часовой бюджет: режим «только защита» (`runtime/brain/state.json`): мозг не вызывает LLM, не исполняет `submit_plan/amend_plan/release_plan`, задания откладываются (попытки не тратятся, TTL `job_ttl_s`),
исполнитель продолжает вести позиции по принятым планам и биржевым стопам. События: `limit_hit brain_budget` или `error BRAIN_DOWN`; выход: `error BRAIN_RECOVERED` (info). Выход при недоступности: проба провайдера основного профиля раз в минуту
(`recovery_tick`), при бюджете: как только окно освободилось. Автоматическое закрытие дня при долгом простое решает ctl (`lifecycle.json:auto_stop_when_brain_down`, по умолчанию выключено).
Бюджет: `budget.day_usd`, `job_usd`, `job_tokens` (на задание, все повторы и запасные внутри него), потолки провайдеров из providers.json.

## Смена модели без перезапуска
`./tb brain use ЦЕЛЬ ПРОФИЛЬ`, кнопка «Агент и модель» (ctl: `brain.use|rollback|reload`), цели: `A.position_manager`, `shared.news_reader`, `position_manager` (роль live-команды), `A` или id агента (все роли команды), `live B` (смена торгующей команды).
Уровни: T0 (общие news_reader/reviewer, любая смена не в режиме live): сразу, достаточно сессии. T1 (live-роль внутри live_team в режиме live) и T2 (смена live_team в live):
- ЖЁСТКИЕ (обойти нельзя): `E_SWAP_NO_LIVE_RIGHTS` (у агента в agents.json нет `live` в modes, `autonomy.live=false`, лимиты не конечны), `E_SWAP_AMBIGUOUS_STATE` (необработанные команды `_inbox`, очередь заданий, планы в placing/blocked/draft,
  ждущие действия, hold по причине brain, неподтверждённые wake-события, hold_reasons исполнителя), `E_SWAP_PROBE` (нет свежей проверки провайдера нового профиля), `E_SWAP_LIMIT_DAY` (не более `max_swaps_day`), `E_SWAP_PHRASE`.
- МЯГКИЕ (принимает владелец по одному, плюс фраза `я принимаю риск`): `W_SWAP_PAPER_HISTORY` (мало paper-сделок/дней или нарушения инвариантов по тегам `agent.<id>`), `W_SWAP_NOT_LIVE_OK`, `W_SWAP_COOLDOWN`, `W_SWAP_NO_AB`.
- Фразы: модель `СМЕНИТЬ МОДЕЛЬ {role} {old} -> {new}`, команда `СМЕНИТЬ ТОРГОВОГО АГЕНТА {old} -> {new}` (шаблоны `swap_rules`). В ctl их проверяет механизм WP12 (nonce, ввод вручную); в терминале нужен TTY и `--confirm`.
Откат: `./tb brain rollback [--to REV]` создаёт НОВУЮ ревизию с содержимым целевой (без фразы и cooldown; отказ, если профиль целевой ревизии исчез или отключён). Автоматические смены (fallback) `live_team` не меняют и ревизию не создают.
Каждая смена: запись `swaps.jsonl` (кто, откуда, куда, пройденные гейты, принятые предупреждения), событие шины `brain_swap` (если тип разрешён в `bus.py`; его добавляет WP14), `last_swap_ts` для предупреждения W4.

## Провайдеры, профили и роли без правки кода (WP-X)
Провайдер добавляется записью в `config/local/providers.json` (дашборд: `llm.provider add`; терминал: `./tb llm provider add ID --preset openai`, шаблоны `./tb llm presets`). Адаптер
`openai_compat` годится для OpenAI/ChatGPT, Gemini (OpenAI-совместимая точка), OpenRouter, Mistral, Groq, Ollama, LM Studio; имена моделей, цены и флаги только в конфиге. Все шаблоны `verified:false`
(НЕ проверены живым ключом): проверка `./tb llm check --provider ID --live`. Ключ: `./tb llm key set ID` (скрытый ввод, файл `<ID>.env` 0600) или поле в дашборде; включить провайдера без ключа нельзя.
Профиль (провайдер + модель + параметры): `./tb brain profile list|set|delete` (слой `config/local/brain.json`; метку `live_ok` ставит только живой eval). Роль: `./tb brain role list|chain|params|budget|clear`:
основной профиль и цепочка запасных (подписанный `active.json`, ревизии, откат `brain rollback`), параметры `temperature|max_tokens|thinking` (профиль, переопределение на роль в `role_opts`) и суточный бюджет роли
`role_opts.<роль>.budget.day_usd` (исчерпан: задания роли откладываются, остальные работают). Профиль для всех ролей: `./tb brain use all ПРОФИЛЬ`. Live-роли в режиме live: смена основного только через
`brain use` с гейтами и фразой; запасные, параметры и профиль live-роли в live не меняются; профиль из цепочки роли удалить нельзя. Контракт для дашборда: `docs/spec_v2/SETTINGS_API.md`.

## Торговый флаг и границы агента
Шлюз (`gateway/registry.trading_allowed`) пропускает `submit_plan` (и ослабляющий `amend_plan`) в режиме не paper только при `state/control/trading.json {day_id, enabled:true, mode:live|testnet, agent, until_ts}` и совпадении `day_id` с `state/control/platform.json`.
Файл нечитаем/отсутствует/неверен = отказ (fail closed). Стоп, закрытие, отмена, hold/release и ужесточающий amend позиции доступны всегда. Теги `agent.<id>` и `model.<профиль>` ставит шлюз сам (`tags.extra`), они попадают в журнал сделок.
Исполнитель берёт лимиты агента (`agents.json`) по тегу `agent.<id>` и передаёт в guard вместе с `setup` (сужение, итог = минимум с уровнем риска); добор требует `pyramid_policy` (уровень риска, exec_limits, allow_add).

## Права для чата Claude Code (предложение, файл настроек не менялся)
`deny`: `Bash(./tb brain use *)`, `Bash(./tb brain rollback *)`, `Bash(./tb brain reload *)`, `Write(state/brain/**)`; `allow`: `./tb brain status`, `./tb brain jobs`, `./tb brain check`, `./tb brain verify`.

## Что проверено на фейках, что нужно на живом ключе
Проверено (`tests/test_brain_*.py`): очередь и приоритеты, слияние дублей, конкурентные воркеры, рестарт, весь путь задание -> решение -> шлюз -> журнал -> ack, повтор формата, запасные профили и охлаждение, бюджет и «только защита», горячая смена между заданиями,
откат, все гейты смены (по одному как единственная причина), сквозной путь через ctl, торговый флаг, теги, секреты (нет в файлах, логах и окружении, нет импортов биржи).
Не проверено: реальные ответы моделей и адаптеры (`./tb llm check --live`, `./tb brain probe --all --live`), качество промптов на живой модели (`./tb brain eval --live --confirm`, WP11-C3), поведение под реальным диспетчером и супервизором дольше минут, Windows.

## Данные в досье для плана дня (struct)
Блок `struct` досье (числа и enum, ≤600 токенов) строится из `runtime/structure.json`, который пишет поток в сервисе `scan` по публичным свечам 5м/1ч (`marketdata/structure.py`): режим, ATR, возвраты, границы дня/вчера/недели, ближайшие уровни `[цена, %, ATR(1ч), тег]`, волатильность и оборот к норме, спред, funding. Через шлюз `get_brief` проходят `struct, limits, risk_level, paper_history, intel, news_digest, memory`. Нет файла -> `missing: [struct]`, роль по промпту обязана вернуть `unclear`. Ручной расчёт: `./tb bybit read levels`.

**Структура по горячим монетам и монетам события.** Состав `structure.json` (по приоритету, до `scan.structure.max_syms`=16, потолок 24): BTC/ETH/SOL; символы открытых позиций; монеты по запросу (`runtime/structure_req.json`, живут 30 мин, до 6); топ-`hot_n` (8) tradable из `hot.json`. Монеты, ушедшие из состава, выбрасываются из свечей и файла. Нагрузка на публичный REST: пауза `pause_s`=2 с между запросами, 5м свечи базовых и позиций раз в `every_s` (60 с), горячих и запрошенных раз в `hot_every_s` (180 с), 1ч свечи раз в 600 / 1800 с (`hot_h1_every_s`); в установившемся режиме около 6 запросов в минуту, прогрев ~11 монет примерно минута. Запрос на монету ставят: сервис `scan` при публикации сигнала (кроме `idea_expired/tp/invalidated`), досье scope=event и `get_brief`, когда по монете события структуры нет; поток структуры просыпается не позже чем через 5 с и подтягивает свечи вне очереди (2 запроса на монету). В досье scope=event `struct` содержит монету задания (раннер передаёт `get_brief` поля `sym` и `seqs`: монета задания идёт первой, события задания всегда остаются в `recent`, даже если после них на шине больше 8 событий; без этих полей монеты берутся из хвоста `recent`, новые первыми) и BTC для режима рынка (до 3 монет, 260 токенов); если записи по монете нет, блок `struct_missing: [SYM]` вместо молчания: роль `entry_scout` отвечает `skip` с `skip_code: no_levels` и не выдумывает уровни (следующий сигнал по монете увидит уже готовую структуру). Запись монеты несёт `ts` (время загрузки 5м свечей). Карточка `/api/brain/watch` показывает `blocks.struct.file_n` (монет в файле), `age_s`, `syms`, `requested`, `requested_wait`.

**Пороги и рамка дня в досье события (2026-10-28).** `session` несёт `max_stop_pct`, `min_rr`, `cost_rt_pct` типа сессии (те же, что у guard): `validate._entry` проверяет стоп и RR после издержек по ним, константы `ENTRY_MIN_RR`/`ENTRY_MAX_STOP_PCT` остаются только без активной сессии. Блок `day` (из `state/control/day_limits.json`, пишет lifecycle S6, не старше 36 ч): `setups`, `avoid`, `max_new_plans`, `size_mult`; коды отказа `SETUP_NOT_ALLOWED`, `SYM_AVOID`, `DAY_NO_PLANS`, `DAY_SIZE`. Детерминированные отказы (`validate.entry_precheck`: `DAY_NO_PLANS`, `WIDE_RANGE` = диапазон 5м события шире `max_stop_pct`, `NO_SLOTS`, `ROOM_CLOSED`, `SYM_BUSY`, `PAUSE_*`) раннер ставит до вызова модели. Обрезанный ответ (`finish=length`): повтор того же вопроса с удвоенным лимитом вывода (до 8192), со второго раза без рассуждений, подсказка по формату не шлётся; адаптер OpenAI-совместимых моделей при включённом thinking добавляет к `max_tokens` запас на рассуждения (1024/4096/8192, не выше `max_out`), так как у DeepSeek они входят в лимит.

**Горизонт сделки выбирает агент (2026-10-28).** Торговый день с дашборда запускает сессию типа `day` (`core/session.py`: бюджет убытка, лимит сделок и срок как у intraday или `risk_profile.day_session`, геометрии у дня нет). Роль entry_scout в `propose` называет `horizon` (scalp/intraday/swing/position): досье события в сессии-дне несёт `session.horizons` с порогами каждого горизонта (max_stop_pct, min_rr, max_leverage), `validate._entry` проверяет стоп и RR по названному горизонту (`HORIZON_UNKNOWN`, в сессии одного горизонта `HORIZON_MISMATCH`), план получает `session_type = horizon`, guard берёт геометрию по горизонту плана, исполнитель принимает план любого горизонта в сессии-дне. План дня: `dayplan.session.type` в торговом дне = потолок горизонта на сегодня (`day_limits.json:max_horizon`, код `HORIZON_ABOVE_DAY`), minutes не больше длительности дня владельца. Конец дня: scalp и intraday закрываются, swing/position идут в чек-лист переноса по политике уровня риска (docs/LIFECYCLE.md).
