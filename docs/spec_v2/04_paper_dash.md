# SPEC V2 / 04. Оценка гипотез (paper/shadow) и дашборд v2

Часть `docs/SPEC_V2.md`. Paper: `logic/paper.py`, `executor/paper_port.py`, `core/expstats.py`, `brain/exp_cli.py` (WP7). Дашборд: `src/tb/dash/*` (WP8). Контекст: `RESEARCH.md` не нашёл системного edge; ценность v2 в дисциплине и в честном измерении гипотез. Поэтому бумажный режим не дополнение, а главный инструмент доказательства.

## 4.1 Paper/shadow режим плана
`plan.mode = "paper"`: исполнитель ведёт план той же машиной состояний (те же условия, правила, трейлы, тейки), но порт вместо биржи это `PaperPort` (реализует `VenuePort`, 06_contracts). Код исполнителя НЕ ветвится по режиму: отличается только порт и журнал (`mode=paper`, теги `shadow`, `paper`). Бумажные планы НЕ занимают слоты, риск и дневные лимиты живых сделок (`guard.day_state` считает только `mode=live`; `guard.evaluate(paper=True)` только размер, WP9).
Жизнь `PaperPort`:
- Данные: те же WS-тики/свечи, что видят живые планы (best bid/ask, last, mark, funding), время ставит система, не мозг; прошлые цены недоступны (нет backdating, защита от lookahead из ref/ai_trader_review.md п.5). Задержка исполнения `paper.latency_ms` (300): сигнал входа исполняется по тику не ранее `t_signal + latency`.
- Рыночный вход: покупка по `ask`, продажа по `bid` на момент `t+latency` плюс проскальзывание `paper.slip_bps` (2 бп, из `costs.bybit.slip`), плюс полуспред уже в bid/ask. Комиссия taker из `risk_profile.costs.bybit.fee`.
- Лимитный post-only вход/тейк: заполнение только когда цена ПРОШЛА сквозь уровень не менее чем на `fill_through_ticks` (1 тик): консервативная модель очереди (touch без прохода не заполняет), комиссия maker `costs.bybit.maker_fee`, цена исполнения = цена лимита; частичных заполнений нет (в журнале это упрощение помечено).
- Стоп: срабатывание по `LastPrice` (как на бирже по умолчанию), исполнение рынком по цене стопа с проскальзыванием `paper.stop_slip_bps` (5 бп) против позиции; гэп через стоп исполняется по худшей из (цена стопа, текущий bid/ask).
- Funding: при пересечении меток 00/08/16 UTC начисляется последняя известная ставка на номинал (знак по стороне).
- Размер: `guard.evaluate(paper=True)` (та же формула риска, без лимитов слотов/дня; без сессии допустимо, `session_type` берёт параметры типа).
- Журнал: `trades.jsonl` с `mode=paper`, `venue=bybit`, `plan_id`, `exp`-теги; `journal analyze --mode paper` и дашборд (фильтр «режим») работают без изменений; MAE/MFE по тикам.
- Дисциплина оценки: бумажный план замораживается (`prereg_hash` на `armed`), параметры правил нельзя менять задним числом (amend после `armed` создаёт новую ревизию, статистика группируется по `(experiment, variant, rev_hash_of_rules)`).

### Теневые варианты и копии
- `shadow_variants` в живом плане: исполнитель создаёт `paper`-планы `PL-...-S1..S3` с `source.kind=shadow`, `parent_plan`, `patch` (JSON Merge Patch только по `entry`, `targets`, `stop`, `manage`, `invalidation`; запрещены `symbol`, `side`, `risk` вверх), одинаковые условия входа: сравнение вариантов A/B на ОДНОМ сигнале (например «с подтверждением и без», «трейл по 3 свечам и по ATR»). Теневой план входит в тот же момент по тем же ценам, что живой (с бумажным проскальзыванием).
- Автотень идей: `./tb plan from-idea I7 --mode paper` строит бумажный план по уровню, стопу и тейку идеи с шаблоном правил. Режим `exec_limits.paper.auto_shadow_ideas` (по умолчанию false, решение владельца) создаёт бумажный план на каждую идею со `status=watching` и заданными level/stop/tp: даёт реалистичный исход (со стопом/тейком/комиссиями) вместо текущих форвардов +15/+60 мин.
- Ограничения: бумажных планов одновременно не более `exec_limits.paper.max_active` (20), по одной монете не более одного одновременно в каждом варианте (иначе коррелированные дубли портят статистику).

## 4.2 Статистика экспериментов (`./tb exp`)
Источник: `state/trades.jsonl` (поля `plan_id`, `exp`, `var`, `setup`, `hyp`, `plan_rev`, `mode`), `state/decisions.jsonl` (для разрезов по правилам).
```
./tb exp list [--mode paper|live|testnet|all]                      эксперименты: n, статус (идёт/достаточно данных), даты
./tb exp stats [--by exp|variant|setup|hyp|rule|symbol|tf_session] [--mode ..] [--min-n 30] [--json]
./tb exp compare EXP A B                                           разность средних R с доверительным интервалом (Уэлч), n и честная оговорка
```
Для группы: `n`, доля плюсовых, средний R и стандартная ошибка, PF, сумма комиссий и их доля от |PnL|, средние MAE_R/MFE_R у выигрышных/проигрышных, доля сделок, закрытых по правилам (`be`, `trail`, `timeout`, `invalidation`), средняя доля реализованного MFE («сколько из хода забрали»), чистая (после издержек) ожидаемость. Правила честности (ref/landscape.md п.3, п.10): при `n < 30` вывод помечен `*` и без вердикта; считается ЧИСЛО сравнений (`K` групп и разрезов в запросе) и выводится поправка Бонферрони для порога значимости; `exp compare` требует `n >= 30` в обеих группах и печатает «не значимо» по умолчанию; сравниваются только планы одной ревизии правил. Результат не меняет лимиты: вывод для владельца (CLAUDE.md: правила меняем только по данным, заранее записав, что проверяем).
Связь с `ideas stats`: тот считает форвард-доходность событий сканера на фиксированных горизонтах; `exp stats --by setup` считает реальные исходы планов со стопами и тейками. `ideas` с планом получают в `ideas list` колонку `plan` (ссылка), `journal analyze` получает флаг `--by exp|var|setup` (WP9): тот же отчёт с разрезом по тегам плана.
Метаданные эксперимента: `config/experiments.json` (необязательный, владелец/мозг): `{"sweep-reject-v1":{"hypothesis":"...","prereg":"что именно проверяем, метрика, объём выборки, критерий","started":"2026-10-28","min_n":30}}`: `exp list` показывает «набрано n из min_n».

## 4.3 Дашборд v2 (`./tb dash`)
Принципы: всё прежнее сохраняется (Обзор, Сделки, Идеи, Рынок, Система, фильтры режима/площадки, тема, подсказки, раскрываемые строки, опрос 4 с, CSP, только GET, Host-проверка). Добавляется слой «система плана». Источники только файлы: `state/plans/*`, `state/decisions.jsonl`, `state/bus/*`, `state/briefs/*`, `runtime/exec_*.json`, `levels.json` (не биржа). Новые модули: `dash/model2.py` (чтение и расчёты; `build_state` в `model.py` добавляет ключ `v2`), `dash/server.py` (новые GET-эндпоинты и список статики), статика `v-plans.js`, `v-decisions.js`, `v-brief.js`, `v-exp.js`, правки `index.html`, `app.js`, `core.js`, `app.css`, `v-overview.js`, `v-system.js`, `v-trades.js`.

### Верхняя полоса «Состояние системы» (на всех вкладках)
Компактная строка-индикатор (расширение текущего пилюли статуса): исполнитель (жив/возраст heartbeat/режим live|testnet|paper|observe), WS public/private (up/down и сколько секунд), REST, `hold` и его причины, KILL (красный баннер на всю ширину с кнопкой-ссылкой «как снять»), очередь событий (backlog не подтверждённых, возраст самого старого wake), сканер, фид, последняя реконсиляция, активная сессия (тип, остаток). Клик раскрывает деталь (как `status-pop`). Любой красный узел = баннер сверху.

### Вкладка «Планы» (доска)
Колонки по состоянию:
- «Наблюдаю»: `armed`, условие входа ещё далеко (цена дальше `zone` от триггера) или нет ордера на бирже;
- «Ждёт входа»: `armed`, в зоне (расстояние до уровня <= 0.3% как у `idea_near`) или условие частично выполнено (`seq` на шаге 2, часть `all`), либо лимит уже стоит на бирже;
- «В сделке»: `entered`/`managing` (дублируется в блоке «Позиции» Обзора);
- «Закрыт» (последние 24 ч): `closed`, `cancelled`, `expired`, `invalidated`, `rejected`.
Карточка: монета и сторона (цвет), тег эксперимента/варианта, режим (live/paper), короткий тезис (`own`, textContent), статус, `rev`; строка «Вход: ...» (человекочитаемое описание условий: «5м прокол и закрытие обратно ниже 142.5 + объём x1.8»), «ближайший триггер»: что именно не хватает и расстояние («цена 141.9, до уровня 0.28%; свеча 5м закроется через 2:10»), TTL осталось, риск USDT и net RR из `guard_preview`, предупреждения (`W_*`). Раскрытие: полный JSON плана (форматированный, сворачиваемый), история ревизий (diff), хронология решений по плану, ссылка на связанный `brief`. Источник описаний условий: `logic/conds.describe` (WP3) вызывается моделью дашборда на данных `levels/exec_snapshot/prices` (расстояние до уровня по цене из `resolve_price`; «свеча закроется через» по часам).

### Блок «Позиции» (Обзор) с правилами сопровождения
Расширение текущих карточек: лесенка цен вертикальной SVG-шкалой (начальный стоп, ТЕКУЩИЙ стоп биржи, вход, текущая цена, тейки t1..tn с состоянием resting/filled, «куда сдвинется стоп» пунктиром: ближайшая цель правила `move_stop`/`trail` по текущим данным), R сейчас и MAE/MFE в R, возраст и остаток `max_hold`. Список правил с состоянием: `ждёт` + причина («нужно +1.0R, сейчас +0.54R»), `выполнено` (время, что сделало, было -> стало), `пропущено` (код: `NOT_TIGHTER`, `ADD_DISABLED`). История действий (последние 10 решений по плану: время, актор, что, результат). Источник стопа и размера: `exec_snapshot.json` (правда биржи), а не оценка журнала; для прежних сделок без плана остаётся прежний расчёт.

### Вкладка «Решения»
Лента `decisions.jsonl` (новые сверху, фильтры: план, актор мозг/исполнитель/владелец, вид действия, только отказы/пропуски, режим). Строка: время, значок актора, план, действие («стоп 143.0 -> 141.9»), «почему» (причина мозга или правило), результат (OK / отказ с кодом, красным), цена и R на момент решения. Раскрытие: `basis` (событие, `brief_id` со ссылкой на вкладку «Брифинг»), args, `link_id`, время ответа биржи. Верхняя сводка за день: сколько решений мозга, сколько отказов Gate и по каким кодам (индикатор дисциплины), сколько авто-действий правил.

### Вкладка «Брифинг рынка»
Последний сохранённый `brief` (или выбранный по `brief_id`): контекст, горячие монеты с числами, уровни выбранных символов (мини-диаграмма уровней дня/недели относительно цены), риск-запас, открытые планы и позиции, чек-лист, последние события. Переключатель «показать на момент решения N» (по `brief_id` из решения). Только то, что видел мозг (числа и enum), поэтому безопасно по тексту.

### Остальные вкладки
- Обзор: добавить полосу состояния, блок «Планы в работе» (счётчики и ссылка), блок «Запас до лимитов» без изменений плюс строка пауз/cooldown (из `protect`), «События» (последние wake).
- Сделки: колонки «План», «Эксперимент/вариант», ссылка на хронологию решений в разворачиваемой строке; разрезы по `exp/var/setup`.
- Идеи: колонка «План» (связь), статус синхронизируется исполнителем.
- «Эксперименты» (новая небольшая вкладка или блок «Сделок»): таблица `exp stats` (n, средний R ± se, PF, комиссии, помечено `*` при n<30), без вердиктов.
- Система: состояние исполнителя (`exec_health` полностью), соединения, backlog шины, KILL и hold, последняя реконсиляция и расхождения, счётчики Gate (отказы по кодам за 24 ч), расход токенов/USD мозга (когда появится API-режим), список процессов (исполнитель, сканер, фид).

### API (все GET)
`/api/v2/state` (одним ответом: верхняя полоса, доска планов с вычисленными расстояниями, позиции с правилами, сводка решений за день, backlog), `/api/v2/plans?status=&mode=`, `/api/v2/plan?id=` (spec, runtime, ревизии, решения), `/api/v2/decisions?after=SEQ&plan=&actor=&kind=&limit=`, `/api/v2/brief?id=` (`last` по умолчанию), `/api/v2/events?after=&limit=`, `/api/v2/exp?by=&mode=`. `model.scrub` применяется ко всем ответам; поля `*key*/*secret*/*token*/*passw*` вырезаются; тест «в ответах и исходниках нет секретов» расширяется на новые файлы. Ограничения размера: решения по 200 за запрос, брифы по запросу.

### Действия владельца (по умолчанию ТОЛЬКО ЧТЕНИЕ)
Прежнее поведение (любой не-GET даёт 405) остаётся умолчанием. Опционально (решение владельца, Q7 в SPEC_V2): флаг `./tb dash --allow-kill` включает один POST `/api/kill`, который только СОЗДАЁТ `state/KILL` (риск снижающее действие), с защитой: слушает только 127.0.0.1, проверка `Host`, `Origin` равен собственному адресу, заголовок `Sec-Fetch-Site: same-origin`, одноразовый токен, выданный страницей при загрузке (в памяти процесса), подтверждение в интерфейсе (двойной клик). Снятие KILL, `flatten`, `resume` только CLI. Пометка решений «требует разбора» (`state/review_marks.jsonl`) не входит в v2.0.

### Дизайн и объём
Не перегружать: по умолчанию на Обзоре видны состояние, позиции с правилами, доска планов свернута до счётчиков; детали по раскрытию. Новые таблицы используют `syncList`/`rowGroup` из `core.js`. Весь пользовательский текст из данных вставляется через `textContent`. Тесты `tests/test_dash.py` и `tests/test_dash_v2.py`: фикстуры планов/решений/событий (в том числе битые строки, пустые каталоги, огромные значения), форматы ответов, отсутствие секретов, неизменность прежних ответов `/api/state` (старые ключи остаются).
