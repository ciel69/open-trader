# WP16: как guard сочетает абсолютные и долевые лимиты, расхождения и решения (2026-10-28)

## Как guard сочетал значения ДО WP16
1. `guard.evaluate` -> `portfolio.scaled_profile(prof, port, venue)`: при equity > 0 абсолютные значения базы ПЕРЕЗАПИСЫВАЮТСЯ долями: `daily_loss_limit_usdt = daily_loss_frac x equity_total`, `margin_per_trade_max = margin_per_trade_frac x equity_venue`, `min_free_reserve = reserve_frac x equity_venue`. Абсолютные `3.0 / 6.0 / 8.0` из `risk_profile.json` действуют только когда equity неизвестен (0).
2. Размер: `risk_budget = equity x risk_per_trade_frac x (0.5 + 0.5 score) x dd_mult x perf_mult`, затем min с остатком дня (`daily_loss_limit + realized - open_risk`), остатком сессии, остатком learning и коррелированной комнатой.
3. `max_open_positions` считает открытые + ждущие лимитные входы; `total_open_risk` как отдельного лимита НЕ было (неявно слоты x риск сделки).
4. Тип сессии подменяет `max_stop_pct`, `min_rr`, `max_leverage = min(база, тип)`.

## Расхождения со спецификацией (п. 4.2) и решения
- (б) Спецификация: абсолютные значения остаются «нижней/верхней границей». Фактически (п. 1) они не применяются при известном капитале. Решение: ничего не менять; уровень задаёт ДОЛИ, абсолют остаётся только запасным значением при equity 0.
- `total_open_risk_frac`: введён как опциональное ограничение `total_open_risk_cap_frac` в эффективном профиле ТОЛЬКО когда оно строже `max_open_positions x risk_per_trade_frac` (уровни 4 и 5). На уровнях 1-3 ограничения нет, поэтому поведение уровня 3 не меняется (при просадке капитала после открытия 2 позиций по 3% сумма могла бы превысить 6% нового капитала: прежний guard это не отклонял).
- Уровень 3 как `identity_level`: пресет НЕ накладывается на базу, возвращается база как есть (проверяется только потолок). Так уровень 3 остаётся точным и для нестандартных профилей (`--profile`), а совпадение пресета 3 с реальной базой фиксирует тест `test_real_config_valid_and_level3_neutral`.
- Лестница просадки: `dd_mult` при первой ступени равен 1.0 (`[0.05, 1.0]`), то есть условие «`dd_mult < 1.0` (просадка >= первой ступени)» из спецификации противоречиво. Решение: авто-понижение срабатывает при просадке >= ПЕРВОЙ ступени лестницы (5%), код причины несёт достигнутую ступень (5%, 10%, 20%).
- Для уровней выше базы (4, 5) пресет ЗАМЕНЯЕТ `risk_per_trade_frac` и `daily_loss_frac` базы (может быть выше базы, не выше потолка). Для 1-2 строже базы.
- `pyramid.allowed` у уровня 3 = false, а `guard.evaluate_add` принимает флаг `a.pyramid_enabled` отдельно: чтобы не менять прежнее поведение (тесты `test_guard_add`), `evaluate_add` уровнем не блокируется, а применяет только эффективный профиль (плечо, маржа). Проверку «уровень разрешает добор» делает исполнитель через `risklevels.pyramid_policy(...)["allowed"]` (WP5).
- Неизвестный `setup` считается классом `mid` (на уровнях 1-2 отклоняется `E_SETUP_AGGR`, на 3-5 проходит).
- Событие шины `risk_level_changed` добавлено в `core/bus.py` (+1 тип; `test_contracts_v2` 24 -> 25), это единственное изменение прежнего теста.
- `brain/brief.py` (поле `risk_level`, до 5 строк) НЕ правился: файл ведёт WP13. Готово для вставки: `risklevels.limits_summary(root, agent_limits, equity)` и `current_level`.

## Правки чужих файлов (минимальные)
`core/guard.py` (импорт, вызовы `effective` в `evaluate`/`_evaluate_paper`/`evaluate_add`, `total_open_risk_cap`, `risk_cap_usdt`, `setup`, ключ `ctx.risk_level` только при уровне не 3), `core/exec_cfg.py` (`warnings()` + `risklevels.exec_warnings`), `core/session.py` (бюджет сессии по уровню в `main`), `core/bus.py` (тип события), `__main__.py` (группа `risk`), `tests/test_contracts_v2.py` (счётчик типов).

## Риски
- Тесты прежних пакетов, работающие с реальным корнем (`test_guard*.py` и др.), читают реальный `state/control/risk_level.json`: если владелец выберет уровень не 3, их результаты могут измениться (новые тесты WP16 изолированы временным `TB_ROOT` и `TB_KEYS_DIR`).
- Удаление файла уровня возвращает уровень 3 (`default_level`), даже если владелец выбрал 1-2; защита: права `deny` на запись `state/control/**` (предлагается в PERMISSIONS).
- Любой код, запущенный от пользователя ОС, может прочитать ключ из `control.json`: граница — права файловой системы и запрет чату читать `~/.config/**`; TTY для `risk level set` и `risk init-key` — дополнительное трение, не граница безопасности.
