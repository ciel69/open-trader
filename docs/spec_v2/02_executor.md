# SPEC V2 / 02. Исполнитель (`./tb exec run`)

Часть `docs/SPEC_V2.md`. Пакет `src/tb/executor/` (WP5) поверх `venues/*` (WP1), `core/*` (WP2, WP4, WP9), `logic/*` (WP3). Исполнитель это детерминированный демон без LLM: принимает планы, вычисляет условия по WS-ценам и свечам, выполняет действия, проверяет лимиты. Единственный держатель торгового ключа в целевой схеме.

## 2.1 Процесс и запуск
- Одна команда: `./tb exec run --profile trade|testnet|paper [--observe] [--max-seconds N] [--keep-entries]`. Профиль ключа читает `launcher.py` (как для `bybit`: `trade` = `bybit_mainnet_trade.env`, `testnet` = `bybit_testnet.env`; `paper` = ключ не нужен, только публичные потоки). Прокси снимаются, как для `bybit`. Из песочницы Claude REST закрыт (403), поэтому запуск как у `scan --watch`: инструментом Bash с отключённой песочницей одной командой `./tb exec run ...` (в фоне) либо владельцем во вкладке Terminal.app/сервисом (рекомендуется: переживает чат).
- `--observe`: режим наблюдения (фаза миграции 1): всё читает и пишет в `runtime/exec_*`, `bus`, но НИКАКИХ записей на биржу и в журнал; план в observe-режиме только `armed/paper`. Нужен для сверки с прежним `sync`.
- Один экземпляр: `runtime/exec.lock` (O_EXCL, внутри pid и время старта; устаревшая блокировка по heartbeat > 30 с или мёртвому pid на POSIX снимается, как в `pending.lock`). Второй экземпляр завершается с кодом 4 и сообщением. Профили `trade` и `testnet` не должны работать одновременно на одном корне (один lock): для тестнета отдельный `TB_ROOT`.
- Сервисы: macOS `launchd` (plist в `docs/spec_v2/runbook.md`, WP10), Windows Task Scheduler. Исполнитель не демонизируется сам; перезапуск после падения делает сервис, потеря времени допустима (стопы на бирже).
- Завершение (SIGINT/SIGTERM, на Windows KeyboardInterrupt): остановить циклы, снять ЖДУЩИЕ ВХОДНЫЕ ордера (они ещё не риск; планы возвращаются в `armed`, `entry.state=waiting`; флаг `--keep-entries` оставляет), НЕ трогать стопы, позиции и reduce-only лесенки (они защищают/фиксируют прибыль на бирже). Событие `exec_stopped`.

## 2.2 Старт: последовательность
1. `state/KILL` проверить первым (его наличие не мешает запуску, но входы запрещены).
2. Загрузить `config/exec_limits.json` (с умолчаниями и валидацией; невалидный файл = отказ запуска), `config/risk_profile.json` (+ sha256 в журнал решений как `profile_hash`).
3. Взять `exec.lock`. Клиент Bybit: синхронизация часов, `account`, `positions`, `open_orders`, `instruments` (кэш `runtime/instruments.json`, обновление раз в час).
4. РЕКОНСИЛЯЦИЯ (2.7) блокирующая. До первого успешного прохода `hold: reconciling`: входы и добор запрещены.
5. Загрузить планы (`PlanStore.list`), восстановить WAL (2.6), подобрать `_inbox`.
6. Для символов активных планов, позиций и `watch`-списка: REST-подкачка свечей (по 200 штук 1м/5м/15м/1ч нужных tf) -> `CandleBook`.
7. Подключить WS (2.4), запустить циклы, событие `exec_started` {env, mode, version, profile_hash, plans, positions}.

## 2.3 Архитектура внутри
- `executor/core.py` класс `Executor`: СИНХРОННАЯ машина состояний с методами `on_ticker`, `on_kline`, `on_private`, `on_timer(now)`, `on_command(cmd)`. Никаких `await`, никакой сети: побочные эффекты только через `VenuePort` и `PlanStore`. Так тесты детерминированы (фейковый порт, фейковые часы).
- `executor/daemon.py`: тонкая asyncio-оболочка. Задачи: публичный WS (тикеры, kline), приватный WS (order/execution/position), таймер (раз в 1 с: ttl, `elapsed`, истечение, heartbeat), `inbox` (опрос раз в 0.5 с), реконсиляция (раз в 30 с), снимок `exec_snapshot.json` (раз в 2 с при изменениях), мост сканера (`scanbridge`), монитор связи. Все REST-вызовы идут через ОДНУ выделенную торговую очередь (`ThreadPoolExecutor(max_workers=1)`), чтение рынка (ticker/kline REST для подкачки) через отдельный малый пул. Так записи на биржу сериализованы (нет гонок «два потока двигают стоп»), а зависший REST читающего пула не блокирует защиту.
- Один `Executor` обрабатывает события ПО ОДНОМУ (очередь событий); долгие REST-операции выносятся в `Action` с последующим `ActionResult`-событием. Для каждой монеты есть замок действий: пока по монете идёт запись (вход, стоп, закрытие), новое действие по ней ждёт (кроме аварийных: закрытие и снятие).
- Время: локальные часы UTC; метки свечей берутся с биржи (`start`); задержка пуша больше `public_price_stale_s` = данные устарели.

## 2.4 Данные: цены и свечи (выбор источника)
Решение: ЦЕНА из WS `tickers.<SYM>` (лучшие bid/ask, last, mark, funding; обновления ~100 мс). СВЕЧИ из WS `kline.1.<SYM>`, `kline.5.<SYM>` (и по необходимости `kline.15`, `kline.60`), поле `confirm=true` означает закрытую свечу; формирующаяся свеча приходит с `confirm=false` (используется только `volume_spike on=live`). REST `GET /v5/market/kline` (уже в белом списке и в `klines.py`) используется для (а) начальной подкачки истории, (б) заполнения дыр после обрыва WS (сравнить последний `start` в книге и текущее время, дозапросить недостающее), (в) проверки подтверждённой свечи при сомнении.
Почему не собственная агрегация из `publicTrade`: объём сделок большой для 6-10 монет, а биржевые свечи уже содержат `confirm`, оборот и точные границы минут; собственная агрегация даёт риск расхождения «закрытая свеча у нас != у биржи» (ровно то, на чём торговые правила TRADING.md основаны: «5м закрылась ниже уровня»). `publicTrade` оставляем как запасной вариант на потом (если понадобятся подсекундные паттерны), интерфейс `CandleBook.on_trade` предусмотреть, но не реализовывать.
Подписки: только для символов активных планов, позиций и списка `watch` (`config/exec_limits.json: watch_symbols`); подписка/отписка динамически при `accept`/терминале плана (лимит символов `exec_limits.connectivity.max_symbols`, умолч. 12).
Защита от плохих данных: цена <= 0, не число, скачок больше `exec_limits.connectivity.max_tick_jump_pct` (умолч. 15% за тик) без подтверждения вторым источником (REST quote) = игнор тика и счётчик `bad_ticks`; больше N подряд = `hold: bad_data`.
Приватный WS: `order`, `execution`, `position`. Нормализация в `venues/bybit_wsx.py` (WP1) с сохранением `orderLinkId`, `execId`, `stopOrderType`, `leavesQty`, `createType`. Дубликаты по `execId` отбрасываются (хранится окно 5000 id и `last_exec_ts`, переживает рестарт).

## 2.5 Gate: единственная дверь к бирже
Каждое действие проходит `executor/gate.py` ДО отправки и логируется (`decisions.jsonl`). Порядок проверок (первое «нет» останавливает):
1. `state/KILL` существует (каждый раз читается файл, без кэша)? Разрешены только `reduce-only`-закрытие, снятие ордеров, подтягивание стопа; если в KILL `flatten:true` — исполнитель закрывает все позиции.
2. `exec` не `--observe`; порт жив; не `hold`, если действие увеличивает риск.
3. Класс действия: `RISK_UP` (вход, добор, постановка входного лимита), `RISK_DOWN` (снять ордер, закрыть, частично закрыть, подтянуть стоп, придвинуть тейк), `NEUTRAL` (поставить лесенку reduce-only). `RISK_DOWN` проходит с минимумом проверок (kill, идемпотентность, монотонность стопа). `RISK_UP` проходит все.
4. Данные: возраст цены <= `entry.max_price_age_s` (3 с), книга/спред доступны, свежесть `portfolio.json` (equity_sync), реконсиляция успешна не старше 2 x `reconcile_every_s`.
5. `RISK_UP` вход: `guard.evaluate(ns)` (ns: символ, сторона, `entry=живая цена`, `sl`, `tp=средневзвешенный`, `score`, `exec=taker|limit`, `contract_max_lev`, режим сессии) должен вернуть `ok:true`; размер/плечо/маржа берутся из ответа, умноженные на `risk.size_mult` (вниз, с повторным округлением по `qtyStep`; если после округления меньше минимального лота: отказ `MIN_SIZE`, не округление вверх). Плюс защиты (2.9). Плюс `symbol_busy`: по монете нет позиции, ждущего лимита (`pending_orders.json`), чужого ордера, другого активного плана.
6. `RISK_UP` добор: `guard.evaluate_add` + `logic/pyramid.check_add` (SPEC_V2 п. 1.7). Любое «нет» это отказ с кодом, мозг получает `action_rejected`.
7. Стоп: монотонность. Новый стоп сравнивается с ТЕКУЩИМ БИРЖЕВЫМ (из последнего `position` WS, при сомнении свежий REST): long: `new >= cur`, short: `new <= cur`; расширять и снимать нельзя. Минимальный шаг (`min_step_ticks`), интервал (`min_interval_s` на монету), зазор от цены (`min_gap_bps_from_price`, чтобы не сработать мгновенно), частота (`max_moves_per_hour`). Нарушение монотонности это не «игнор», а `INVARIANT_VIOLATION`: событие `error` + запись; такое не должно случаться при исправном движке правил (защита в глубину: правила, Gate, `bybit_exec.set_stop`, валидатор).
8. Скорость: токен-бакет записей (`rate.rest_write_rps`), ограничение «не больше N отправок по монете за 10 с».
9. Идемпотентность: действие получает `action_id` и `link_id` (детерминированные от `plan_seq` и счётчика действий плана, 2.6); повторное действие с тем же `action_id` не отправляется, а сверяется с результатом.
Ответ Gate: `allow` (с итоговыми параметрами) или `deny(code, detail)`; `deny` пишется в журнал решений, а при коде из списка «будящих» (`action_rejected`) отправляется событие в шину. Коды: `KILL`, `HOLD`, `STALE_PRICE`, `GUARD`, `MIN_SIZE`, `SYMBOL_BUSY`, `COOLDOWN`, `RATE`, `STOP_NOT_TIGHTER`, `INVARIANT_VIOLATION`, `ADD_*` (см. SPEC_V2 1.7), `OBSERVE`, `SESSION`, `LIMIT_PLANS`, `PRICE_JUMP`.

## 2.6 Идемпотентность, WAL, перезапуск
- `link_id` (orderLinkId, <= 36 символов): `tbx-<plan_n>-<action_n>`, где `plan_n` целое, присваиваемое плану при `accept` (счётчик в `state/plans/_counters.json`), `action_n` растёт в рантайме плана и сохраняется ДО отправки. Не пересекается с `pending.LINK_RE` (`P[TM]-...`): мост приватного WS различает свои и чужие ордера по префиксу `tbx-`.
- WAL по плану: перед любой записью на биржу в `decisions.jsonl` дописывается запись `kind:"intent"` (action_id, тип, параметры, link_id, `profile_hash`, `plan_rev`) с `fsync`; после ответа `kind:"result"`. В `runtime.json` плана хранится `pending_actions: [action_id...]` (атомарная замена файла до отправки).
- Восстановление при старте: для каждого `pending_actions`: ордер -> `order_by_link(sym, link_id)` (realtime, затем history): найден = применить как результат (`recovered:true`), не найден и прошло больше 15 с = считать не отправленным, снять из `pending_actions`; `set_stop` -> сверить биржевой стоп с целью; `close` -> сверить размер позиции. Слепых повторов нет.
- Ошибка записи на биржу классифицируется: `rejected` (биржа явно отказала, retCode != 0: ордера нет), `unknown` (таймаут/обрыв: ордер мог создаться: ВЕСТИ СЕБЯ как «возможно есть», проверять по `link_id`), `rate` (10006: пауза и повтор через токен-бакет только для идемпотентных `set_stop`), `position_gone` (110017/34040-подобные: позиции нет -> реконсиляция/финализация). `rejected` повторяется только по новому решению правил, `unknown` никогда не повторяется без проверки.
- Журнал сделок (`trades.jsonl`) пишется после ПОДТВЕРЖДЁННОГО заполнения; запись `open` содержит `plan_id` (ключ идемпотентности как `pending_id` у лимитов: повторная обработка не задвоит).

## 2.7 Реконсиляция (старт, каждые 30 с, после переподключения WS)
Источники истины: биржа для размера, средней цены, стопа, ордеров, исполнений; журнал и планы для намерений. Алгоритм:
1. Прочитать `positions`, `open_orders`, `executions(since last_exec_ts)`, `account`.
2. Сопоставить владельцев: позиция по монете имеет владельца `plan` (в `runtime.json` плана и/или в записи журнала `plan_id`), `legacy` (в журнале открытая запись без `plan_id`), `unknown` (журнала нет).
3. Таблица расхождений:
   - План `armed` с входным ордером в `runtime`, но на бирже ордера нет и позиции нет: ордер отменён/отклонён/исполнен-и-закрыт: поднять статус по исполнениям или вернуть `entry.state=waiting`; событие `reconcile_alert` только при необъяснимом.
   - План `entered/managing`, позиции на бирже нет: позиция закрыта извне (стоп/тейк/ликвидация/вручную): ФИНАЛИЗАЦИЯ: собрать закрывающие исполнения (`executions`/`closed-pnl`), посчитать выход (средневзвешенный), причину (`sl`/`tp`/`manual`/`liquidation` по `stopOrderType`/цене, как `cmd_sync`), снять оставшиеся ордера по монете, записать `close` в журнал (идемпотентно: если запись уже закрыта, не писать), `position_closed`, идея, cooldown, статус `closed`.
   - Размер на бирже != ожидаемому, и исполнений нет: `position_drift` -> `hold` плана + событие (wake); если размер меньше (кто-то закрыл часть вручную): принять факт, пересчитать лесенку (снять лишние reduce-only, пересчитать `qty`); если больше (кто-то добрал вручную): `hold` + wake, НИЧЕГО не добирать и не закрывать самим.
   - Стоп на бирже отсутствует (`stopLoss == 0`) у позиции плана или `legacy`: немедленно выставить стоп из плана (`current_stop`) через `set_stop`, если цена уже за ним — закрыть по рынку (как `verify_protection`); событие `reconcile_alert: missing_stop` (wake). У `unknown` позиции стоп НЕ ставится и позиция не трогается: только событие.
   - Стоп на бирже строже ожидаемого планом: принять (кто-то подтянул вручную). Шире ожидаемого: вернуть к ожидаемому (допустимо только как восстановление защиты; это единственный случай «вернуть стоп»).
   - Лесенка: не хватает reduce-only ордеров относительно `runtime.targets` -> поставить; лишний `tbx-` ордер без цели плана -> снять; неизвестный чужой ордер -> событие `unknown_order`, не трогать.
   - Позиция владельца `legacy` или `unknown`: только наблюдение, `exec_snapshot` и события; управление только через `adopt`.
   - Баланс: `account` -> `equity_sync` (2.9).
4. Результат реконсиляции пишется в `runtime/exec_health.json` (`last_reconcile_ts`, `diffs`) и в журнал решений при расхождениях. Пока `diffs` не пуст и не разрешены, новые входы блокируются (`hold`).

## 2.8 Частичные исполнения и гонки
- Вход рыночный: может прийти несколькими `execution`. Вход считается завершённым, когда ордер `Filled` или прошло `entry.fill_wait_s` (2 с) после первого исполнения; средняя цена по исполнениям; стоп встроен в ордер (применяется к позиции по мере исполнения).
- Вход лимитный post-only: первое частичное исполнение -> отмена остатка (как `bybit_limit.process_one`: усреднения нет), `partial:true`. Гонка «заполнился между опросом и отменой» решается повторным чтением ордера по `link_id`.
- Тейки лесенкой: частичные исполнения reduce-only ордеров обновляют `targets[i].filled_qty`; `target_filled` = `filled_qty >= qty`. Правила, подписанные на цель, ждут полного исполнения.
- Гонка «стоп сработал / исполнитель двигает стоп»: `set_stop` на закрытую позицию даёт `position_gone`; обработчик не считает это сбоем, а запускает финализацию.
- Гонка «команда мозга отменить план / вход заполнился»: команда `cancel` на `armed` с ордером в полёте: снять ордер, перечитать, и если есть заполнение — статус `entered` и результат команды `E_STATUS_FORBIDS cancel: filled` (мозг получит событие входа и сможет `close`).
- Два события для одной монеты в одной миллисекунде: порядок определяется очередью `Executor` (FIFO); состояние читается из `runtime.json` после каждого шага.
- Ордера лесенки при частичном закрытии стопом/вручную: размер reduce-only ордеров не должен превышать оставшуюся позицию: после любого изменения размера пересчёт и `amend`/пересоздание.

## 2.9 Защиты и дневные лимиты
Работают поверх `guard` (который остаётся главным и неприкосновенным) и только СУЖАЮТ разрешённое. Значения в `config/exec_limits.json` (файл владельца).
- Из `guard`/`risk_profile.json` (не дублируются): дневной лимит убытка, серия стопов `max_consecutive_stops`, `max_open_positions`, бюджет и срок сессии, лестница просадки, `learning`, корреляционный потолок, `max_stop_pct`, `min_rr`.
- Из TRADING.md (формализация существующих правил владельца): пауза по монете после стопа (`symbol_cooldown_after_stop_min: 30`); после двух стопов подряд общая пауза 60 минут и вход только со свечным подтверждением (`pause_after_consecutive_stops: {n:2, minutes:60, require_confirm:true}`); вход без подтверждения только с `size_mult <= 0.5` и тегом `no-confirm`. Все паузы считаются ЧИСТОЙ функцией от истории закрытых сделок журнала (`logic`-подобный `executor/protect.py`, без собственного состояния, значит переживают перезапуск).
- Новые (для исполнителя): `max_entries_per_hour` (4), `max_entries_per_day` (12), `max_plans_active` (6), `max_submits_per_hour` (20), `max_stop_moves_per_hour` (30), `max_actions_per_symbol_per_10s` (4). Превышение частоты входов: событие `limit_hit`, дальнейшие входы блокируются до конца окна. «Аномальный рост числа сделок» (в 3 раза выше среднего за 7 дней) = `hold: anomaly` до подтверждения владельца (идея TradeTrap из `landscape.md`).
- Режим только уменьшения (`reduce_only` флагом `hold: reduce_only`): включается при `drawdown_halt`, при `equity_mismatch`, при ручной команде; разрешает только `RISK_DOWN`.
- `equity_sync`: каждые 60 с исполнитель читает `account`; если `portfolio.json` для площадки старше `stale_after_s` или расходится с биржей не более чем на `max_dev_frac` (10%), он вызывает `portfolio.set_venue(...)` (обычный дрейф PnL); большее расхождение (пополнение/вывод) = `hold: equity_mismatch` + wake: владелец или мозг делает `./tb portfolio set/deposit`. Решение сознательно НЕ автоматическое для больших скачков: ложная просадка от вывода остановила бы торговлю, а ложный рост поднял бы лимиты.

## 2.10 Потеря связи и деградация
| Что пропало | Детектор | Поведение |
|---|---|---|
| Публичный WS | нет сообщений дольше `public_price_stale_s` (10 с) | цены для условий не свежие -> входы и условные правила по цене приостановлены; REST-подстраховка: опрос `quote` раз в 2 с по символам с позициями; событие `connectivity` при `down_s >= 20` |
| Приватный WS | `DownMonitor` > `private_ws_down_hold_s` (20 с) | `hold: private_ws` (входы и добор запрещены); защитные действия через REST-опрос позиций раз в 3 с; на восстановлении полная реконсиляция |
| REST | N ошибок подряд / `rest_blind_s` (60 с) без успеха | `hold: blind`; новых записей на биржу не делать, кроме аварийного закрытия позиции без стопа; событие wake `connectivity` |
| Всё | нет ни WS, ни REST | исполнитель ничего не может; позиции защищены биржевым стопом; при возврате связи реконсиляция; событие `connectivity` (wake) отправляется после возврата с `down_s` |
| Исполнитель упал | `exec_health.json` устарел > 20 с | дашборд красный; `events --follow` печатает синтетическое `exec_down`; позиции под биржевыми стопом и лесенкой. Сервис перезапускает |
Принцип: после возврата связи сначала реконсиляция, затем (только если расхождений нет) снятие `hold`. Логика «догнать пропущенное»: правила по свечам обрабатывают пропущенные ПОДТВЕРЖДЁННЫЕ свечи после подкачки REST (в порядке времени), но входы по устаревшим условиям не исполняются (окно `entry.max_price_age_s` и `max_chase_bps` защищают); `ttl` и `invalidation` отрабатываются сразу.

## 2.12 Действия по этапам сделки (последовательности)
Вход (RISK_UP): Gate -> `set_leverage` (110043 не ошибка) -> запись `intent` -> `place_entry` (market либо post-only limit) со встроенным `stopLoss` (`tpslMode Full`, `slTriggerBy` LastPrice) -> `result` -> ожидание исполнений (WS `execution`/REST) -> `entered`: (1) прочитать позицию, убедиться что `stopLoss > 0` (нет = аварийно `set_stop`, если не вышло — `close_market`), (2) записать `open` в журнал (теги `plan:ID`, `exp:`, `var:`, `setup:`, `no-confirm` при необходимости; `ctx` через `tradectx.snapshot`, плюс `plan_ctx` со свечами 5м и условием), (3) идея `taken` (`ideas.mark_idea`), (4) лесенка (reduce-only), (5) `managing`, событие `entry_filled` (wake).
Тейк исполнился (WS `execution`, reduce-only): обновить `targets`, правила `target_filled`, событие `milestone target_filled` (wake).
Подтягивание стопа: правило/команда -> Gate (монотонность) -> `set_stop(tighten_only=True)` -> read-back через WS `position` (стоп изменился) либо REST; если не подтвердилось за 5 с: повтор ОДИН раз после проверки, затем событие `error`.
Закрытие: Gate (RISK_DOWN) -> снять reduce-only лесенку нужной доли -> `close_market(qty)` -> финализация по факту (WS `position` size=0 / реконсиляция).
Финализация: `trade close` в журнал с агрегированным выходом (`journal.cmd_close` с `pnl_override`, см. WP9), `path` из собственного трекера цены (точнее скана: WS-тики), снять висящие ордера, `cooldown` считается из журнала, идея, событие `position_closed` (wake), план `closed`.
