# WP5: проверка исполнителя на testnet

Дата: 2026-10-28. Площадка: Bybit **testnet** (UNIFIED, SOLUSDT, tick 0.01, шаг 0.1). Запуск: `TB_ROOT=<scratchpad>/tn ./tb exec run --profile testnet` (отдельный корень: копия `config/`, пустой `state/`, сессия intraday, `watch_symbols=[SOL]`), планы через `./tb plan ...` в тот же `TB_ROOT`. Размер сделок 0.1-0.2 SOL (`risk.size_mult=0.003`; баланс testnet 9978 USDT, поэтому без уменьшения guard дал бы сотни SOL). Mainnet не запускался, ключи не читались. После прогона: позиций и ордеров на testnet нет, процессов нет.

## Найденные проблемы
1. **КРИТИЧНО (исправлено).** После рестарта реконсиляция подтягивала `executions` за 6 часов и приписывала ЧУЖИЕ и старые исполнения (старые команды `tbx-w...`, исполнения других планов, ручные сделки с пустым link) текущему плану как «добор»/«закрытие»: в `pos.entries` появились чужие «add», PnL и объём были неверны. Теперь: (а) исполнение принадлежит плану только по своей ссылке `tbx-N-M` с его `plan_n`; чужая непустая ссылка не принадлежит никому; пустая ссылка (стоп/ликвидация/ручное закрытие) только после входа плана; (б) `last_exec_ts_ms` и окно 5000 `exec_id` хранятся в `runtime/exec_state.json` и переживают рестарт; (в) без сохранённого состояния реконсиляция смотрит 10 минут. Регрессионные тесты есть.
2. **КРИТИЧНО (исправлено).** Единичный ПУСТОЙ ответ `position/list` без объясняющих исполнений (сбой биржи на testnet, воспроизведён: план был ложно финализирован как `manual`, лесенка снята, позиция осталась без управления; стоп на бирже, к счастью, остался) принимался за закрытие позиции. Теперь закрытие признаётся только если исполнения покрывают вход, либо пустой ответ повторился 3 раза подряд на протяжении 5 с. Тесты есть.
3. **Зависания REST ~16 с (подтверждено, чаще, чем в WP1A: 2 из 25 последовательных запросов).** Единственный рабочий поток исполнителя в это время не может ни закрыть позицию, ни подтянуть стоп (KILL flatten занял 65 с). Смягчено транспортом `executor/transport.py`: чтение с таймаутом 4 с и одним повтором на новом соединении, запись с таймаутом 9 с без повтора (исход `unknown` проверяется по link_id). Задержка KILL flatten 10 с. Радикальное решение (постоянное соединение keep-alive, отдельный поток защитных операций) отдано WP1B: правка `venues/bybit.py` не моя.
4. `guard_preview` при приёме показывает риск полного размера guard (до `size_mult`): `risk_usdt 119.7` при фактическом размере 0.2 SOL. Для живой работы `size_mult` не используется для масштабирования до таких величин, но preview стоит пересчитывать с учётом size_mult (WP10/мелкая правка в `commands.guard_summary`).
5. Событие `kill` пишется дважды: `exec halt` (CLI) и сам исполнитель при обнаружении файла. Дубликат безвреден (оба `state: on`).
