# SPEC V2 / 08. WP15: память случаев (база опыта для агента)

Часть `07_control_lifecycle_news_roles.md` (ссылка в п. 7.1 и 0 там). Дата: 2026-10-28. Статус: СПЕЦИФИКАЦИЯ. Пометки [A] (зависит от WP11-A: gateway, agents.json), [C3] (WP11-C3: роли reviewer/morning_analyst/position_manager), [W9] (WP9: journal/tradectx, уже готовы).

Решение владельца: «дневник» это не текст для человека, а история и база опыта ДЛЯ АГЕНТА: перед решением агент получает похожие прошлые ситуации, их исходы и действующие уроки (гипотезы) и опирается на них. Человек тоже может смотреть (вкладка «Память»), но это вторично.
Принципы: (1) память ничего не разрешает и не запрещает (разрешения только guard, Gate, agents.json); она лишь подсказка и контекст; (2) малая выборка = без громких выводов (n<30 везде помечено); (3) только числа, enum, идентификаторы и короткие собственные формулировки системы, никакого текста третьих лиц; (4) только информация, доступная в момент решения, попадает в «ситуацию» (против ретроспективной предвзятости); (5) всё детерминировано и считается stdlib без сети и без LLM (LLM только предлагает вывод ревьюера, который проходит валидатор).

## 1. Запись случая
### 1.1 Файл и схема `tb.case/1`
`state/cases.jsonl`: append-only, одна строка JSON, запись под блокировкой `state/cases.lock` (`filelock.FileLock`), `seq` монотонный. Случай не редактируется: дополнение результата и вывода = НОВАЯ строка того же `case_id` с `rev` +1 и `kind="update"` (читатель сворачивает по `case_id`, берёт последнюю ревизию по полям; хеш-цепочка `prev/h` как у decisions, проверка `./tb memory verify`). Размер строки <= 3 КБ.
```json
{"schema":"tb.case/1","seq":41,"case_id":"C-20261027-DOOD-01","rev":2,"kind":"new|update","ts":"2026-10-27T13:39:43Z",
 "type":"trade|skip|idea|signal",
 "refs":{"journal_id":"BB-M-DOOD-1027-1522","idea":"I1","plan":"PL-1027-DOOD-01","brief_id":"B-20261027-1330-01","event_seq":1810,"outcome_id":"I1"},
 "src":{"risk_level":3,"actor":"agent|owner|system","agent_id":"api","model":"ds-pro","role":"position_manager|morning_analyst|chat|manual","exp":"sweep-reject-v1","var":"A","rules_ver":"2026-10-27","mode":"live|paper|testnet","mem":"on|off"},
 "situation":{
   "sym":"DOOD","coin_class":"meme|major|alt_mid|alt_small|stock_token|unknown","side":"long|short|watch",
   "setup":"level_reclaim|level_reject|sweep_reject|breakout_retest|range_fade|trend_pullback|momentum_chase|manual|none","hyp":"код-гипотеза или null",
   "regime":"trend|range|volatile|unclear|unknown","btc_ret_1h_pct":-0.3,
   "range_5m_pct":1.8,"range_15m_pct":3.1,"ret_5m_pct":1.2,"turn_surge_5m":5.4,"chg_24h_pct":-12.3,
   "spread_bps":4.9,"funding_pct":-0.39,"stop_pct":0.9,"rr_planned":1.8,"size_mult":0.5,
   "utc_hour":13,"utc_session":"asia|europe|us|overlap","dow":2,
   "confirmed":true,"confirm_kind":"candle_close|none|unknown","no_confirm_tag":false,
   "blackout":false,"fng":23,"dvol":null},
 "decision":{"action":"enter|skip|wait|exit|stop_move","why":"<=200","conf":0.6,"stop_dist_vs_range5":1.4},
 "result":{"status":"open|closed|expired|na","r":-1.07,"pnl_r_net":-1.1,"mae_r":-1.2,"mfe_r":0.1,"hold_min":16,"exit_reason":"sl|tp|manual|timeout|invalidation|rule|kill|session_end","fees_r":0.05},
 "whatif":{"h_min":15,"dir_pct":10.5,"ret_pct":-10.5,"cost_pct":0.24,"net_dir_pct":10.3,"src":"hot_outcomes","outcome_id":"I2"}|null,

```
Правила полей: `situation` фиксируется в момент решения и не меняется ревизиями (проверка: update не может изменить `situation`/`decision`); числа округляются (проценты 2 знака, bps 1); неизвестное = `null` (не 0); словарь `coin_class` определяется детерминированно по справочнику (`major`={BTC,ETH}, `stock_token` по `instruments.json`/маске, остальное по обороту: порог в `config/memory.json`); `rules_ver` = дата редакции правил (из `config/memory.json:rules_ver`, владелец поднимает при изменении правил: случаи разных версий не смешиваются по умолчанию); `src.model`/`agent_id` ставит КОД из контекста вызова (шлюз), не LLM; `mem` = включена ли память у агента на момент решения (нужно для A/B, п. 5).
Приватность: в случае нет ключей, адресов, абсолютных сумм капитала/баланса/позиции в USDT; только доли и R. `risk_usdt`, `pnl_usdt` НЕ хранятся (только R и проценты); номинал/маржа не хранятся. Символ хранится (публичная информация).

### 1.2 Виды случаев
- `trade`: решение войти, результат из журнала сделок (закрытие; R, MAE/MFE из `path`, причина, комиссии).
- `skip`: осознанный пропуск с кодом причины (`why` + `skip_code` из enum: `NO_CONFIRM, WIDE_STOP, RANGE_GT_STOP, COOLDOWN, BLACKOUT, SPREAD, SIZE, NO_EDGE, CORRELATED, OTHER`) из решений мозга (`decisions.jsonl kind=skip`, `entry_blocked`, ответ `morning_analyst` по `watch`), результат `whatif` подтягивается позже.
- `idea`: идея из `ideas.jsonl` (watching/taken/expired/invalidated), результат из `hot_outcomes.jsonl` по id.
- `signal`: сигнал сканера без решения (только если `memory.record_signals=true`, по умолчанию false: шум; нужен для базовой частоты «что происходит после такого события»).

### 1.3 Кто и как пишет
1. Код-писатель `memory/writer.py` (детерминированный, основной): (а) при закрытии позиции (событие `position_closed`/запись `close` в журнале) строит случай `trade` из `plan`/`spec`, `journal.open` (`ctx`, `plan_ctx`, `tags`), `path`, решений (`decisions.jsonl` по плану), `brief` по `refs.brief_id`; (б) при пропуске (`skip`, `entry_blocked`, `plan_rejected` по гейту безопасности, невыбранный watch) строит `skip`; (в) при появлении итога по идее/событию в `hot_outcomes` создаёт или обновляет `whatif`. Вызывается из ctl/lifecycle (хук `day.stop` C-шаг и событие `position_closed`) и командой `./tb memory sync` (идемпотентно по `case_id`). Вызовы чистые, без сети.
2. Роль `reviewer` [C3] через инструмент шлюза `add_case_review(case_id, review)` [A] (новый инструмент, право `memory.review`): заполняет блок `review` (строгая схема ниже); один вывод на случай; повтор = отказ; пишет `kind=update`. Ревьюер получает вход ТОЛЬКО из `situation`, `decision`, `refs` и результата; блок `whatif` и `result` показываются ему отдельно и помечены «после решения», а правило задания требует отделять «что было известно» от «что вышло».
3. Владелец вручную: `./tb memory add --file case.json` (для переноса опыта, источник `owner`) с тем же валидатором.
Валидатор `memory/schema.py`: типы, диапазоны, enum, длины (`why` 200, `lesson`/`better` 200, списки <= 5), regex символов `^[A-Z0-9]{2,20}$`, запрет неизвестных ключей, очистка текстов (`sanitize.clean_own`: NFKC, управляющие и невидимые символы, URL и длинные base64/hex удаляются, схлопывание пробелов, обрезка); ЛЮБОЙ текст, пришедший из `state/intel/items.jsonl` или заголовков, в случай не попадает (слои, п. 6). `ctx`-поля берутся из tradectx числами; `thesis`/`note` в случай НЕ копируются целиком (идея и сделка содержат длинный текст: берётся только `why`, укороченный до 200, и только из собственных записей системы).

### 1.4 Вывод ревьюера `review` (строгая схема `tb.casereview/1`)
```json
{"schema":"tb.casereview/1","verdict":"good_process|bad_process|unlucky|lucky|unclear",
 "right":["confirm_waited","stop_beyond_extreme","size_ok","skipped_bad_range"],
 "improve":["no_confirm","chase","wide_stop","tight_stop","size","ignored_cooldown","blackout","fee_drag","wrong_direction","late_exit","none"],
 "alternative":{"action":"wait_confirm|skip|smaller_size|wider_stop_skip|other_side|exit_earlier|hold_longer|none","detail":"<=160"},
 "known_at_decision":["range_5m_gt_stop","funding_extreme","no_confirm"],
 "lesson_hint":{"code":"L-<enum>","cond":"тип условия из словаря п. 4.2"}|null,
 "conf":0.6}
```
Все списки только из enum (нет свободного текста, кроме `alternative.detail`, очищаемого). `known_at_decision` ⊂ перечня признаков, вычислимых из `situation` (валидатор проверяет, что названный признак действительно истинен по `situation`; ложное утверждение = вывод отклоняется: защита от ретроспективной предвзятости и галлюцинаций). `verdict=unlucky|lucky` допустим, только если `result` отличается от ожидания процесса (хороший процесс при минусе / плохой при плюсе) по явному правилу (код сам предлагает кандидатов; LLM подтверждает). Теги `improve` согласованы с тегами ошибок LESSONS (`no-confirm, chase, tight-stop, wide-stop, wrong-direction, ...`), мэппинг в `tags.err` детерминированный.

## 3. Поиск похожих ситуаций (stdlib)
### 3.1 Нормализация и сходство
Модуль `memory/similar.py` (чистый, без `os/socket/urllib/open`; чтение файлов в `memory/store.py`). Вектор признаков -> сходство Gower взвешенное: `S(a,b)=Σ w_i·s_i / Σ w_i` по признакам, где значения у обоих известны (неизвестное пропускается и снижает `coverage`).
- категориальные: `s=1` если равны, иначе `0` (для `regime`, `side`, `utc_session`, `coin_class`, `setup`, `confirm_kind`); частичное сходство для `setup`-семейств (таблица `config/memory.json:setup_family`: `level_reclaim~level_reject` 0.5);
- числовые: нормировка на размах по эталонным диапазонам из `config/memory.json:scales` (не по данным: стабильно при малом n), `s=max(0,1-|x-y|/scale)`; для логарифмических (`turn_surge_5m`, `range_5m_pct`, `spread_bps`) расстояние в `log1p`;
- булевые (`confirmed`, `no_confirm_tag`, `blackout`): равенство;
- циклические (`utc_hour`): `min(d,24-d)/12`.
Веса по умолчанию (`w`): `side` 3, `setup` 3, `confirmed` 3, `regime` 2, `range_5m_pct` 2, `range_15m_pct` 1, `stop_pct`/`stop_dist_vs_range5` 2, `turn_surge_5m` 1.5, `spread_bps` 1, `funding_pct` 1, `coin_class` 1.5, `utc_session` 1, `btc_ret_1h_pct` 1, `fng` 0.5, `size_mult` 0.5. Веса и шкалы в `config/memory.json`, владелец меняет; тесты фиксируют порядок на фикстурах.
### 3.2 Фильтры и выбор
Жёсткие фильтры (до расчёта): `mode` (по умолчанию случаи `live` и `paper` считаются РАЗДЕЛЬНО: запрос `scope=same_mode|all`, умолчание `same_mode`+подсказка отдельной статистикой по другому режиму), `rules_ver` (по умолчанию текущая и предыдущая, `rules=any` включает все), `side` (по умолчанию совпадать для trade/skip; `watch` не фильтруется), `type`, `exclude_from_stats=false`, не старше `max_age_days` (по умолчанию 90). Порог `min_sim` (0.55) и `coverage>=0.6`. Top-k (по умолчанию k=8, максимум 20) по убыванию сходства; ничья: свежее, затем `case_id`. Детерминизм: результат зависит только от входа и файла (тест).
### 3.3 Агрегат
По отобранным: `n`, `n_closed` (с результатом), `mean_r` ± `se` (стандартная ошибка = sd/√n; при n<3 не считается), `win_rate`, `median_r`, `mean_mae_r`, `mean_mfe_r`, частоты тегов `err` (топ-3 с долями), `rule_followed_no_share`, `skip_whatif` (для пропусков: средний `net_dir_pct` после издержек и доля, где пропуск был «верным»), разрезы `by=side|setup|model|confirmed` по запросу. Всегда выводится `min_sim_used`, `avg_sim`, `coverage`.
### 3.4 Малая выборка и честность
Поле `warn`: `n<5` -> `INSUFFICIENT` (числа показываются, но блок помечен «нет статистики; это только примеры»); `5<=n<30` -> `LOW_N` («n<30, выводов не делаем», как в TRADING.md); `n>=30` без поправки на множественные сравнения -> `OK_NO_MULTIPLE` (для разрезов by= используется Бонферрони из `expstats.bonferroni`). Агрегат НЕ содержит слов «рекомендуется/надо»: только факты и предупреждение. Дополнительно показывается «базовая частота»: средний `r` по всем закрытым случаям того же режима для сравнения (чтобы +0.2R не казалось много при общем +0.3R).
### 3.5 Интерфейсы
CLI `./tb memory`:
```

stats   [--by err|setup|side|model|confirmed|coin_class] [--mode live|paper|testnet] [--since D] [--min-n 5]    сводка по базе (тот же ряд, что journal analyze, но по случаям)
```

Код выхода 0 при ok. Вывод JSON одной строкой по умолчанию.
Инструмент шлюза [A] `get_similar_cases` (право `@memory.read`, только чтение): вход `{sym?, side?, setup?, k<=10, scope, features? (числа из белого списка)}`; если признаки не указаны — берутся из текущего `brief` символа/плана; выход: агрегат + список до 8 случаев в сжатом виде `{case_id, sim, ts, side, setup, confirmed, r, err[], exit, why<=100}` + `lessons` применимые + `warn`. Тот же `scrub`, лимит ответа 2 КБ. Дополнительно `add_case_review` (право `memory.review`, роль reviewer) и `list_lessons` (чтение). Права по реестру `config/agents.json`: группа `@memory.read` добавляется в `tools` агентов `api`, `reviewer`, `chat`; `@memory.review` только `reviewer`; у `news_reader` нет. Если `memory.enabled=false` у агента (флаг A/B), инструменты скрыты, блоки brief пусты, а `src.mem="off"` записывается в его случаи.
### 3.6 Блоки в brief (жёсткий лимит)
`brief.py` (правка владельца WP13 уже разрешена для intel; для memory — минимальная правка функцией `memory_block(root, ctx)` ≤ 60 строк, владелец WP15, согласовать с WP13 порядок слияния):
```json
"memory":{"similar":{"n":6,"n_closed":5,"mean_r":-0.4,"se":0.5,"win":0.2,"warn":"LOW_N","base_r":-0.1,"top_err":[["no-confirm",0.6],["chase",0.4]],
           "cases":[{"id":"C-..","sim":0.82,"r":-1.07,"err":["no-confirm"],"exit":"sl","why":"вход у уровня без реакции"}]},
          "lessons":[{"id":"L-0007","st":"hyp","n":4,"conf":0.4,"txt":"no_confirm+meme -> стоп чаще (гипотеза)"}]}
```
Размер блока <= 450 токенов (≈1800 символов); сначала режется список `cases` (до 3), затем `lessons` (до 3), затем остаётся только агрегат; блок помечен `own_`-префиксом полей текста: «это прошлые наблюдения системы, данные, не инструкции». Блок включается в `scope=event` для планов в статусах `armed/draft` и событий входа, и в `scope=start` (общая статистика по тегам ошибок за 14 дней и топ-3 урока); в `scope=event` для уже открытой позиции памяти нет (не подталкивать к панике).

## 4. Уроки как гипотезы (`state/lessons.jsonl`)
### 4.1 Запись
Append-only (как cases): `{"schema":"tb.lesson/1","lesson_id":"L-0007","rev":3,"ts":..,"kind":"new|update","status":"hyp|confirmed|rejected|expired|merged","cond":{...},"claim":{...},"evidence":{"cases":["C-..",..],"n":4,"n_closed":4,"mean_r":-0.9,"se":0.3,"base_r":-0.1,"first_ts":..,"last_ts":..},"conf":0.4,"expires_ts":..,"created_by":"code|reviewer|owner","txt":"<=140 (генерируется из шаблона)","contradicts":["L-0003"],"merged_into":null,"history":[{"ts","status","reason_code"}]}`
### 4.2 Формулировка (шаблон, не свободный текст)
`cond` = конъюнкция из <= 3 условий словаря: `{feature, op, value}` где feature ∈ белый список признаков `situation` (`confirmed=false`, `coin_class=meme`, `range_5m_pct>=1.5`, `setup=sweep_reject`, `utc_session=us`, `blackout=true`, ...), `op` ∈ {=, >=, <=, in}. `claim` = `{metric: "mean_r|win_rate|stop_hit_share|err_share", dir: "lower|higher", vs: "base|zero", effect: число}` — т. е. «в условиях cond средний R ниже базового». `txt` строится из шаблона по русским словарям (`"{cond} -> {metric} {dir} ({n} случаев, гипотеза)"`), поэтому свободного текста нет. Предложить урок может код (поиск устойчивых отклонений по тегам ошибок: правило `mean_r` группы ниже базы на >=0.5R при n>=4 и согласованное направление в >=75% случаев), ревьюер через `lesson_hint` (код+условие, затем код проверяет по данным и создаёт урок только если статистические предпосылки выполнены) или владелец. Максимум создаваемых кодом уроков в сутки: 3.
### 4.3 Жизненный цикл
- `hyp` (гипотеза): создана, n мало; мозг видит с пометкой «гипотеза, проверять».
- `confirmed`: при `n_closed>=30` по условию (или `>=15` и ожидаемый эффект с `|mean - base|>2*se` без поправок; с поправкой Бонферрони на число активных уроков) в РАЗНЫХ днях (>=5 дней) и разных режимах рынка (не один эпизод), ИЛИ подтверждено владельцем. Подтверждённый урок остаётся рекомендацией для мозга, не правилом: превращение в правило guard/TRADING = только владелец вручную (`lesson promote` печатает черновик правки, не применяет).
- `rejected`: новые случаи опровергают (`mean_r` по условию >= базы при n_new>=10 или эффект сменил знак), или владелец.
- `expired`: срок годности `ttl_days` (по умолчанию гипотеза 30, подтверждённая 90) истёк без новых подтверждающих случаев; затухание уверенности: `conf_eff = conf * 0.5^(возраст_без_подтверждений / half_life)`, `half_life=21` день; ниже 0.15 урок скрыт от brief (в базе остаётся).
- `merged`: близкие по условию (перекрытие >0.8 по Жаккару признаков и совпадающий claim) объединяются, ссылки сохраняются.
Новые случаи пересчитывают уроки командой `lesson refresh` (в `memory sync`): для каждого активного урока считается число подходящих по `cond` случаев с даты создания, обновляются `evidence`, `conf` (=1-exp(-n_eff/10) с поправкой на se, максимум 0.9 для hyp), и статус по правилам выше. Каждое изменение статуса записывается строкой `update` с `reason_code` (`ENOUGH_N, CONTRADICTED, EXPIRED, MERGED, OWNER`).
### 4.4 Противоречия
Два активных урока противоречат, если `cond` пересекаются (все условия одного совместимы с другим) и `claim.dir` противоположны. Оба получают `contradicts`, `conf` каждого умножается на 0.6, в brief показываются ОБА с пометкой «противоречат»; код предлагает уточняющее условие (если расщепление по признаку даёт согласованные подгруппы, создаётся пара более узких гипотез). Урок, у которого есть подтверждённое противоречие с `confirmed`, не может стать `confirmed`.
### 4.5 Вытеснение
Максимум активных уроков в brief 3 (по `conf_eff * применимость`); в базе максимум 200 активных (`max_active_lessons`), при превышении вытесняются expired/rejected, затем с наименьшим `conf_eff`; случаи при росте файла сворачиваются (п. 6.4).

## 5. Оценка пользы памяти (A/B) [ОТЛОЖЕНО: по умолчанию выключено]
Решение владельца: параллельные модели для сравнения (две paper-команды на одних событиях) сейчас не нужны из-за расхода токенов. Раздел сохранён как будущая возможность: включается `brain.json:trading.compare.enabled=true`, до этого ничего не запускается и не тратит токены. В объём и оценку WP15 (15a, 15b) НЕ входит; доступны только дешёвые способы оценки без второй модели: ретро-тест на истории (п. 5, пункт 5, `./tb memory backtest`) и сравнение периодов с включённой/выключенной памятью у основного агента (метка `mem` в случаях), с оговоркой, что это «до/после», а не A/B.
Цель: проверить, что агент с памятью принимает решения лучше, а не что память «выглядит умной».
1. Дизайн: две paper-команды на ОДНИХ событиях (механизм сравнительных команд 07b п. 6.2, ОТЛОЖЕНО, работает в paper-дне): `A` = `mem:on` (инструмент `get_similar_cases` доступен, блок `memory` в brief), `B` = `mem:off`; одинаковая модель, одинаковые промпты, версия правил, лимиты; различие только в памяти. Теги `agent.<id>`, `mem.on|off`, `model.<profile>` на планах (ставит шлюз), в случаях `src.mem`. `exp stats --by mem` (разрез добавляет WP15 в `expstats`/`exp_cli` как small-правку или через собственный `memory stats --by mem`, если правка чужого файла нежелательна).
2. Что сравниваем (заранее записано, предрегистрация в `state/plans/` как гипотеза `mem-ab-v1`): (а) доля сделок с нарушением правил (`rule_followed != yes`) и с тегами ошибок; (б) средний R после издержек; (в) доля пропусков, которые whatif признал верными; (г) число сделок (память не должна просто «замораживать» торговлю: потеря возможностей = минус); (д) стоимость токенов. Главная метрика — (а) и (б) вместе; (д) справочно.
3. Критерии: минимум 30 закрытых сделок в каждой ветке и не менее 10 торговых дней; парное сравнение по событиям, на которых обе ветки приняли решение; различие значимо при p<0.05 после Бонферрони по 3 метрикам; практический порог: разница mean R >= 0.2R ИЛИ снижение доли нарушений >= 15 п. п. при не худшем R. Иначе вердикт «польза не доказана» (память остаётся включённой только как справочник без влияния на live).
4. Как не обмануть себя: (1) память пополняется только случаями ДО текущего решения (утечка будущего: `ts` случая < `ts` решения, `get_similar_cases` фильтрует по `as_of`); (2) обе ветки пишут в РАЗДЕЛЬНЫЕ срезы памяти или читают общую базу без собственных свежих случаев другой ветки (иначе B «подсматривает» через общую базу): параметр `memory.isolation: per_agent|shared_history` (рекомендуется `shared_history` из миграции + `per_agent` для новых); (3) нельзя настраивать веса/пороги памяти по результатам этого же A/B (параметры фиксируются до старта, `rules_ver` и `memory_cfg_hash` записываются в эксперимент); (4) рынок: A/B внутри одних и тех же дней и событий, а не «до/после»; (5) множественные сравнения; (6) не останавливать эксперимент по первому «хорошему» результату (длительность и n фиксированы); (7) `mem` ветки меняется только остановкой и новым экспериментом; (8) отчёт показывает доверительные интервалы, а не только средние, и явную оговорку при n<30.
5. Кросс-проверка без LLM: «ретро-тест на истории»: для каждого закрытого случая искать похожие ТОЛЬКО среди более ранних и оценивать, предсказывает ли агрегат знак результата лучше базового (брайер/точность знака, n и интервал); отчёт `./tb memory backtest`. Ожидание: на n~20 вывода нет; тест запускается по мере роста базы.

## 6. Защита от отравления и prompt injection, размеры, приватность
1. Источники записи: только код-писатель, ревьюер через шлюз (валидатор), владелец. Брэйн-роли (analyst/pm) НЕ имеют права писать случаи или уроки (нет инструмента). `add_case_review` принимает только enum-поля и `alternative.detail` (очищается и обрезается; `detail` не показывается мозгу в brief, только в дашборде и по `show`; в brief идут enum-коды и `why` из СОБСТВЕННЫХ решений до 100 символов).
2. Тексты: любые поля свободного текста проходят `sanitize.clean_own` (п. 1.3) + эвристику `inj_suspect` (как в 07 п. 3.4); подозрительная строка заменяется кодом `[redacted]` и случай помечается `flags:["inj_suspect"]`, в brief он не попадает. Слои (правило для `test_layering`): `tb.memory` не импортирует `tb.intel.items`, не читает `state/intel/items.jsonl` и не использует поля новостей; поле `refs.event_seq` ссылается на событие шины, но текст события не копируется (в шине нет текстов третьих лиц).
3. Отравление фактами: ревьюер не может поменять `situation`/`result` (их пишет код); вывод ревьюера отклоняется при ложных `known_at_decision`. Один источник не может создать подтверждённый урок (нужны >=5 дней и >=N случаев из разных планов); `created_by=reviewer` без статистической поддержки остаётся `hyp` с `conf<=0.3`. Случаи агента с `mem=off` или с `exclude_from_stats` не поднимают уроки.
4. Размеры: строка случая <= 3 КБ, файл `cases.jsonl` до 20 МБ (около 6000 случаев); ротация: старше `retention_days` (по умолчанию 365) сворачиваются в `state/cases-archive/YYYY.jsonl.gz` без потери агрегатов (индекс `state/cases.idx.json` — компактные признаки для поиска, пересобираемый); чтение индекса O(n) на 5000 случаях < 100 мс (тест). `lessons.jsonl` до 2 МБ. Блок brief <= 450 токенов, ответ инструмента <= 2 КБ, `get_similar_cases` не чаще 30 вызовов/час на агента.
5. Приватность: в случаях и уроках нет ключей, токенов, путей, адресов, абсолютных USDT-сумм (equity, pnl, margin) — только R, проценты, доли; тест-сканер `memory.privacy_scan(case)` (запрещённые ключи `pnl_usdt, equity, margin, notional, balance`, паттерны ключей) вызывается при записи и в `verify`. Вывод в дашборд/чат тот же.
6. Целостность: хеш-цепочка, `verify`, бэкап (`memory export` в сжатый файл); битая строка пропускается и считается; параллельные писатели безопасны (блокировка).
7. Смена версии правил: при поднятии `rules_ver` старые случаи остаются, но не участвуют в поиске по умолчанию и не подтверждают новые уроки; уроки, опиравшиеся на старую версию, получают `expires_ts` через 14 дней, если не подтверждены новыми случаями.

## 7. Дашборд: вкладка «Память» (`dash/static/v-memory.js`, `memory/dashapi.py`, чтение)
Подключается через `EXT_API/EXT_SCRIPTS` (07 п. 1.8). Разделы: (1) «Случаи»: таблица (дата, символ, сторона, сетап, подтверждение, R, причина выхода, теги ошибок, источник/модель, режим), фильтры, карточка случая (ситуация, решение, результат, whatif, вывод ревьюера, ссылки на сделку/идею/план/досье); (2) «Поиск»: форма «найти похожие» (символ/сторона/сетап/признаки или «из текущего плана»), результат тем же агрегатом с предупреждением n; (3) «Уроки»: список с статусом hyp/confirmed/rejected, n, conf_eff, основание (ссылки на случаи), противоречия, кнопки владельца (подтвердить, отклонить, продлить срок) через `ctl`-команды `lesson.confirm|reject|expire` (требуют только сессию и CSRF; подтверждение ≠ правило); (4) «Статистика ошибок»: частоты тегов `err`, `rule_followed` по неделям, mean R по тегам, A/B `mem` (когда идёт). Все тексты через `textContent`; текст ревьюера и `detail` показываются экранированными. Тест dashapi: ответы без секретов, быстро на 5000 случаев.

## 9. Риски и вопросы владельцу
Риски: (1) переобучение на малом n и ложные «уроки» (смягчение: n<30 предупреждения, гипотезы, затухание, A/B); (2) ретроспективная предвзятость ревьюера (валидатор `known_at_decision`, разделение «известно» и «исход»); (3) память подталкивает к избеганию сделок и потере возможностей (метрика числа сделок в A/B, память не запрещает ничего); (4) отравление через текст (нет свободного текста, enum, санитайзинг, права); (5) смешение режимов/версий правил (жёсткие фильтры); (6) раздувание brief (жёсткий лимит); (7) нестабильность признаков из старых записей (`null`+`missing`, не парсить заметки); (8) A/B с параллельными моделями отложен (расход токенов); до включения оценка пользы только ретро-тестом и сравнением периодов.
Вопросы (рекомендации по умолчанию): Q-M1 показывать ли памяти live-мозгу сразу или только после положительного A/B (рекомендую: в paper сразу, в live после вердикта, до этого блок `memory` только в подсказках с пометкой справочно); Q-M2 включать ли `record_signals` (рекомендую нет на старте); Q-M3 срок хранения случаев (рекомендую 365 дней с архивом); Q-M4 кто подтверждает уроки (рекомендую только владелец; код лишь предлагает, `confirmed` по статистике не превращается в правило автоматически); Q-M5 считать ли сделки «проверка механики» и ручные «выбрано пользователем» случаями (рекомендую хранить, но исключить из статистики и уроков); Q-M6 минимальные пороги `confirmed` (n_closed>=30, >=5 дней) подтвердить; Q-M7 `isolation` для A/B (рекомендую `shared_history` из миграции + раздельные новые).
