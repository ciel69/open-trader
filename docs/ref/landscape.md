## 1. Паттерны архитектуры у сильных проектов

1. Единое ядро для бэктеста/paper/live (NautilusTrader, freqtrade dry-run, Jesse). Стратегия не знает, где она. Уверенность В.
2. Event-driven шина: данные -> сигнал -> риск -> исполнение как отдельные обработчики событий; события детерминированно воспроизводимы из лога. У нас уже есть фид и мониторы, не хватает единого журнала событий как источника правды (С).
3. Риск-движок стоит между стратегией и биржей и умеет состояния типа "активно / только уменьшение / остановлено" (в Nautilus - trading state, из памяти, Н). Решение стратегии - это заявка, а не приказ.
4. Идемпотентность и реконсиляция: стабильный client order id, который не меняется при ретрае; сверка внутреннего журнала с биржей при старте и периодически; восстановление после падения между "отправил" и "записал" (источники: статьи по идемпотентным пайплайнам, NexusTrader docs; С).
5. Kill-switch на двух уровнях: локальный (флаг-файл/лимит просадки) и биржевой (cancel-all, dead-man timer типа cancel-after-timeout; на Bybit у нас стоп/тейк на стороне биржи, это уже лучшая защита) (С).
6. Мультиагентные LLM-проекты (TradingAgents, ai-hedge-fund, QuantAgent) почти все повторяют граф: аналитики -> дебаты/триаж -> трейдер -> риск. Риск-агент там обычно тоже LLM, то есть не жёсткий. У нас правильнее: LLM предлагает, детерминированный `guard.py` решает (наше преимущество).
7. Память: слои (краткая/долгая), рефлексия после сделки и периодическая (FinMem, TradingGPT, TrustTrade, TradingGroup). Всё проверено на бэктестах акций, не на live (В по наличию, Н по эффективности).
8. (Подтверждено кодом, см. раздел 7) Двухстадийный конвейер "решение без ордеров -> исполнение позже с повторной проверкой лимитов" (ai-hedge-fund) и хэш-цепной леджер с kill switch в файле; в TradingAgents исполнения нет вовсе, риск там - LLM-дебаты.
9. Разделение "мозг без ключей / исполнитель с ключами": в найденных open-source проектах встречается редко (в поиске этого вообще не нашлось); MCP-серверы бирж обычно хранят ключ в env самого клиента. Это пробел рынка и наш дизайн-принцип, а не заимствование.

## 2. Алгоритмы и подходы к риску и исполнению

- Риск как доля капитала, стоп и тейк при открытии, один контракт - одна позиция: у нас уже есть; совпадает с практикой.
- Protections в стиле freqtrade: пауза N минут после серии стоп-лоссов по инструменту; общий стоп торговли при просадке за окно; пауза по соотношению убытков. Реализуется как чистая функция от `state/trades.jsonl` внутри `guard.py` (параметры взять из docs freqtrade, из памяти не копировать).
- Reduce-only режим при просадке: после порога разрешены только закрытия.
- Дневной/сессионный лимит числа сделок. Alpha Arena показывает перетрейдинг LLM (одна модель ~1400 сделок за раунд, источник вторичный), а TradeTrap - рост числа сделок с 47 до 391 при порче промпта: рост частоты сделок - индикатор сбоя.
- Модель издержек: комиссия 0.09% на сторону taker плюс проскальзывание и funding должны быть в `guard` как порог "ожидаемый ход >= k * издержки". 10 bps издержек - стандарт в строгих работах (BlindTrade).
- Исполнение: лимитные/post-only входы, где возможно, чтобы платить maker; стоп-ордера на стороне биржи; проверка состояния биржи перед ретраем (у нас уже в CLAUDE.md).
- Размер позиции от волатильности (ATR) при заданном риске в деньгах: стандарт; у нас фактически уже так.
- Не усреднять убыток, не повышать риск после просадки (у нас в правилах).
- По коду (раздел 7): срезанная лимитом экспозиция не перераспределяется на другие позиции (ai-hedge-fund `apply_limits`), каждый срез логируется с before/after; protections freqtrade блокируют только входы и никогда выходы; локи хранятся с причиной и временем окончания.

## 3. Методологические ловушки оценки

Источники: FINSABER (2505.07078), BlindTrade (2603.17692), "What survives honest evaluation?" (2608.27734), "Summoning the Oracle" (2605.24564), аудит 30 работ "Beyond Agent Architecture" (вторичный пересказ, статья не открывалась), StockBench, LiveTradeBench, Alpha Arena.

1. Lookahead: данные из будущего в промпте; более тонко - параметрический lookahead: модель "помнит" рынок из обучающих данных, поэтому бэктест на периоде до даты отсечки модели недостоверен. Лекарство: окна строго после отсечки модели, анонимизация тикеров/дат (BlindTrade), либо только live/forward.
2. Выживание и узкий юниверс: преимущества LLM исчезают на длинных периодах и широких наборах активов (FINSABER). Для нас - не выбирать "лучшие 3 монеты" задним числом.
3. Data snooping / число перебранных конфигураций: надо считать число проверенных вариантов и поправлять значимость (2608.27734). У нас есть "поиск системных стратегий закрыт" - это согласуется.
4. Валовые против чистых результатов: издержки торговли, funding, стоимость инференса часто не учтены. На 40 USDT фиксированные издержки доминируют.
5. Тайминг исполнения: сигнал по закрытой свече, исполнение по следующей цене; иначе завышение.
6. Короткие окна и дисперсия: Alpha Arena и LiveTradeBench - недели; один сезон ничего не доказывает. У нас крайне малая выборка сделок: до сотен сделок нельзя утверждать edge.
7. Non-determinism LLM: один прогон - не результат; нужны повторные прогоны и доверительные интервалы.
8. Чёткая честная оценка по нашему проекту: считать edge недоказанным до forward-теста на достаточном числе сделок после издержек. Выводы статей по акциям нельзя переносить на крипто-перпы напрямую (уверенность С).

## 4. Интеграция LLM: сессия, API или гибрид (по опыту проектов)

- Почти все open-source LLM-трейдеры - API-пайплайны с графом ролей (LangGraph/LangChain) на дневном цикле. Дорого по вызовам, но воспроизводимо и логируемо. Alpha Arena тоже по API, с единым промптом.
- Сессия (как у нас): мозг один, длинный контекст, гибкость; минусы - непрозрачность, нет детерминированного воспроизведения, зависимость от живой сессии.
- Рекомендация-гибрид (мой вывод, не из проектов): детерминированный слой (фид, события, guard, исполнитель, kill-switch) работает всегда; LLM вызывается по триггеру (событие прошло фильтр) через API с структурированным выводом (tool use/JSON schema) и возвращает только "заявку" (инструмент, сторона, тезис, уровни). Исполнитель с ключами проверяет заявку через guard. Prompt caching для статичной части (правила, профиль риска, журнал). Агентов-специалистов (триаж новостей, постмортем) можно вынести на более дешёвую модель. Стоимость токенов как параметр: считать USD на сигнал и на сделку и включать в чистую доходность.
- Для самообучения: рефлексия по журналу после сделки (немедленная) и по периоду (расширенная) - но записывать выводы как гипотезы с проверкой, а не как правила, пока нет статистики.

Что НЕ брать (дополнено кодом): риск как LLM-дебаты (TradingAgents), fallback "достать решение из текста" для торговых действий, сторонний скрининг постов, копирование кода freqtrade (GPL-3.0; идеи ок), целочисленные акции и NY-календарь из ai-hedge-fund.

Что НЕ брать (первоначальный список):
- Мультиагентные дебаты LLM как есть: дорого, нет доказательств прибыли после издержек, риск-агент не должен быть LLM.

- Код под GPL/AGPL (freqtrade, OctoBot, backtesting.py): только идеи.

### 7.1 TradingAgents (Apache-2.0, по тексту LICENSE)

Архитектура по коду (`tradingagents/graph/setup.py`, LangGraph): параллельные аналитики (market, social/sentiment, news, fundamentals, у каждого свой подграф с лимитом раундов tool-вызовов `max_tool_rounds`, после лимита принудительный "wrap-up") -> Bull/Bear дебаты (`should_continue_debate`, счётчик раундов) -> Research Manager (deep-модель) -> Trader -> три риск-аналитика (Aggressive/Conservative/Neutral, по кругу) -> Portfolio Manager -> END. Параллельно работает "Memory Log".

Как решение становится ордером: никак. Выход графа - `final_rating` из enum Buy/Overweight/Hold/Underweight/Sell (структурный вывод `PortfolioDecision` через `with_structured_output`) и markdown. Trader выдаёт `TraderProposal` с необязательными `entry_price`, `stop_loss`, `position_sizing` (последнее - строка свободного текста). В `backtest.py` прямо написано, что системе нечего исполнять: нет количества, цены исполнения, кассы, и бэктест "must not grow" портфельный симулятор. Риск-"проверки" в коде нет: "риск-менеджмент" - это дебаты трёх LLM-персон, итог решает LLM. Детерминированных лимитов позиции, плеча, просадки я не нашёл (grep по broker/place_order/max_position ничего значимого не дал).

Что реально защищает от ошибок модели и данных:
- Структурный вывод со схемой и fallback на свободный текст с парсингом рейтинга (`structured.py`, `rating.py`). Fallback - слабость: при сбое схемы рейтинг достаётся регуляркой из текста.
- Комментарии в коде отмечают, что рейтинг берётся из типизированного поля, а не из текста, чтобы цитата в тезисе его не подменила.
- Лимит раундов tool-вызовов, лимиты раундов дебатов, `DEBATE_PATH_MAP` против падений графа.
- Для источников текста: `post_screen.py` - опциональный скрининг соцпостов внешним сервисом TypeSafe (нужен ключ, это сторонний вызов - не брать); `report_html.py` экранирует вывод модели в HTML. Санитайзинга рыночного текста от prompt injection в промптах не нашёл (grep по inject/sanitiz/untrusted даёт только про разметку отчёта и "инъекцию контекста"). То есть новости и посты идут в LLM как есть. Вывод: цитаты о TradeTrap/adversarial news к этому проекту применимы.

Lookahead по коду: есть реальная point-in-time дисциплина для ДАННЫХ: `dataflows/date_window.py` обрезает окна до даты прогона, нормализует время в UTC, исключает верхнюю границу, недатированные новости в историческом прогоне отбрасывает ("a backtest cannot prove it is not from the future"), отдаёт плейсхолдер "unavailable", если фид не покрывает окно, и не выдаёт сегодняшние снимки в историческом прогоне (`withhold_live_profile`). Уроки памяти фильтруются по "point-in-time cutoff" (`memory/settlement.py`, `trading_graph.py`, ссылки на issue #1251). Но параметрического lookahead (LLM знает рынок из обучения) защиты нет: ни анонимизации, ни проверки даты отсечки модели (grep по cutoff/contaminat/memoriz: только про cutoff памяти). Бэктест-сетка `iter_grid` не идёт дальше сегодняшнего дня. Бэктест оценивает "качество решения", а не прибыль.

Память (`memory/log.py`, `settlement.py`): append-only markdown-файл; запись о решении без вызова LLM; через N дней `settle_pending` считает реализованную и альфа-доходность против бенчмарка региона и вызывает Reflector (2-4 предложения), результат подмешивается в промпт Portfolio Manager как "Lessons". Разделитель записей - HTML-комментарий; есть file lock и опциональная ротация. Вывод: это лёгкая и переносимая идея постмортема (запись решения -> отложенная оценка по рынку -> короткий урок), но уроки LLM-генерируемые и непроверяемые.

Слабые места: нет детерминированного риска и исполнения; решение - дискретный рейтинг без калибровки; десятки LLM-вызовов на одно решение (дебаты x 2 + 3 риск-персоны + 4 аналитика + менеджеры); нет защиты от инъекций; акции и дневной цикл; нет учёта издержек в оценке.

Можно взять как идею:
- Отложенный settlement решений с альфой против бенчмарка (для нас: BTC/ETH-бенчмарк и/или "ничего не делать") и короткий урок в журнал: модуль `journal`/`review`, трудоёмкость малая-средняя, польза средняя.
- Паттерн лимита раундов tool-вызовов и принудительного wrap-up для сессии: малая, средняя.
- Point-in-time окна и плейсхолдер "unavailable, не отсутствие" для данных с дырами: малая, средняя.
- Тип/enum решения плюс отдельная проверка типов (рейтинг из поля, не из текста): малая.
Нельзя: дебаты как источник решения без детерминированного риска; fallback "достань решение из текста" для торговых действий (у нас при сбое схемы - не торговать); внешний скрининг постов сторонним API.

### 7.2 ai-hedge-fund (MIT, по тексту LICENSE: "MIT License, Copyright (c) 2024 Virat Singh")

Важное: текущий репозиторий не тот, что описывали в обзорах (`src/agents/*`). Код теперь пакет `hedge_fund/` (~20k строк с тестами и TUI) с идеей "fund as a living system" (VISION.md: пока многое "aspirational", ROADMAP.md; README и VISION заявляют educational only, не для реальной торговли). Это уже существенно зрелее, чем обычно пишут.

Архитектура по коду: `Fund` = аллокатор над стратегиями; стратегия = набор аналитиков (LLM-персоны и квант-модели с общим интерфейсом `predict(ticker, as_of, view) -> Signal`) + политика портфеля; сигнал - `Signal(value ∈ [-1,1], reasoning, horizon_days)`. Конвейер двухстадийный (`pipeline/stages.py`):
1. `assess_fund(as_of)`: берёт только закрытую сессию (`clock.is_complete`), аналитики читают данные через `PinnedQuotes` (цена фиксируется как закрытие сессии, "никогда не провод"), сигналы смешиваются (`blend_signals`) в целевые веса, затем детерминированный `apply_limits` (`risk/limits.py`) и `validate_targets`. Результат - DecisionRecord без ордеров и без брокера.
2. `execute_decision(session)`: исполнение на СЛЕДУЮЩЕЙ сессии (должна быть строго позже `as_of` и завершена); если информационный cutoff сдвинулся, решение пересчитывается; затем `build_orders` (чистая функция: цели минус позиции, округление вниз до целых акций, сначала продажи), проверка проецируемой позиции и gross против лимитов ещё раз ДО `broker.place_order`.

Где проверка риска: `risk/limits.py` - "Conviction requests, risk disposes": жёсткие `max_position_pct` и `max_gross_exposure`, проверка isfinite, срезанная экспозиция не перераспределяется (остаётся в кэше), каждый срез пишется как `ClampEvent` для аудита. Плюс повторная проверка после построения ордеров и `validate_targets`, который пересчитывает вклад из сигналов и отказывает, если запись не совпадает с мандатом. Риск не LLM - это главное отличие от TradingAgents и совпадает с нашей архитектурой.

Защита от lookahead (по коду): сильная для данных - разделение "оценка на закрытии T-1, исполнение на закрытии T", `Clock.previous()` как information cutoff, `PinnedQuotes`, хэш-цепочка ледгера. Параметрический lookahead (знание LLM) - не нашёл защиты (grep пусто). `scorecard/` оценивает сигналы по `horizon_days` - то есть есть встроенная оценка калибровки аналитиков.

Леджер (`paper/ledger.py`): append-only, по файлу на сессию, каждая запись содержит хэш предыдущей; состояние (позиции, кэш, ожидающее решение) никогда не хранится отдельно, а восстанавливается сверткой цепи, "поэтому нечему расходиться"; разрыв/подмена записи ломает `replay`; чекпойнты - кэш цепи. `control.json` - kill switch: читается в `FundState.halted`, и `advance` проверяет его первым, так что никакой клиент не может торговать остановленный фонд (`pipeline/session.py`, `FundHalted`). Это очень близко к тому, что нам нужно.

LLM-слой (`llm/client.py`): абстракция `LLMClient.complete(system, user)`, провайдеры включая Anthropic; JSON извлекается `extract_json`; комментарий в `assess_fund` про prompt-cache при повторном вопросе одной персоне. Детали валидации ответов не исследовал.

Слабые места: ориентирован на акции (целые акции, NY-сессии, дневные закрытия); нет реального live-брокера по умолчанию (paper); нет реконсиляции с биржей (брокер абстрактный); в README и VISION прямо нет claims о доходности; тесты большие, но это не доказательство edge. Решения в рамках одной сессии не реагируют на события.

Можно взять как идею (по убыванию пользы):
1. Двухстадийное разделение "решение (без ордеров) / исполнение (позже, по свежему состоянию)" и повторная проверка лимитов на спроецированной позиции непосредственно перед отправкой: модуль `guard.py`/исполнитель, малая-средняя, высокая.
2. `ClampEvent`: каждый срез лимита пишется в журнал с before/after, срезанное не перераспределяется: малая, средняя-высокая.
3. Хэш-цепной append-only леджер с восстановлением состояния сверткой и `replay --verify`: новый модуль `ledger`, средняя, высокая (основа реплея и аудита).
4. Kill switch как файл `control.json`, проверяемый первым в точке входа любого клиента: малая, высокая.
5. `Signal` с `horizon_days` и scorecard по горизонту: средняя, средняя.
6. `PinnedQuotes`: LLM читает ту же цену, по которой исполнитель маркирует, и никогда "провод": малая, средняя.
Нельзя: целочисленные акции/NY-календарь; код TUI; зависимость от их платных data-провайдеров. Лицензия MIT позволяет брать код, но адаптация нужна всё равно.

### 7.3 freqtrade (GPL-3.0, по тексту LICENSE: GNU General Public License v3; брать только идеи)

Архитектура по коду (`freqtradebot.py` 2840 строк): синхронный цикл `process()`: перезагрузка рынков -> дозаполнение комиссий -> открытые сделки из БД (SQLAlchemy) -> обновление данных -> `strategy.analyze` -> `manage_open_orders` и `exit_positions` под `_exit_lock` (защита от коллизий с force_exit из другого потока) -> корректировка позиций -> вход только если `state == RUNNING` и есть свободные слоты. Сначала выходы, потом входы; на старте `startup_update_open_orders` перечитывает открытые ордера с биржи (`fetch_order_or_stoploss_order`), ордера старше 5 дней считаются отменёнными; `handle_onexchange_order` ищет неизвестные ордера через `fetch_orders`, когда баланс "пропал". Это реконсиляция постфактум.

Как решение становится ордером: стратегия (код пользователя, не LLM) даёт сигнал -> проверки: `is_pair_locked` (локи протекшенов), `get_trade_stake_amount` (с `tradable_balance_ratio`/`available_capital`, `max_open_trades`), опционально depth-of-market -> `execute_entry` -> `exchange.create_order` -> лишь ПОСЛЕ ответа биржи создаётся/обновляется запись `Trade`/`Order` в БД. Вывод: окно между "биржа приняла" и "записано в БД" существует; freqtrade в `create_order` не передаёт свой `clientOrderId` (по grep в exchange/*.py `clientOrderId` встречается только в разборе ответа bitget) и `create_order` не обёрнут в `@retrier`, то есть слепого ретрая нет, зато нет и идемпотентного ключа: осиротевший ордер подхватывается лишь `handle_onexchange_order`. Для нас идемпотентность через собственный `orderLinkId` строго лучше (на Bybit он есть; то, что именно так и сделано в нашем коде, я не проверял).

Protections (`plugins/protections/*`, `protectionmanager.py`): четыре класса - `StoplossGuard` (N стоп-лоссов/ликвидаций с прибылью < порога за окно -> глобальный или парный лок, опционально по стороне), `MaxDrawdown` (просадка по закрытым сделкам за окно, режимы ratios и equity), `CooldownPeriod` (пауза по паре после закрытия), `LowProfitPairs`. Реализация: чистые функции от истории закрытых сделок в БД; результат - запись `PairLock` с `until` и причиной; `ProtectionManager` вызывается после закрытия сделки (`handle_protections`), а проверка `is_pair_locked` стоит прямо перед входом. Локи блокируют только ВХОДЫ, выходы идут всегда (reduce-only по смыслу). Валидация конфигурации (нельзя одновременно stop_duration и unlock_at). Это именно то, что нужно перенести в `guard.py`: простая модель "история сделок -> лок до времени с причиной".

Выход и kill-switch: `rpc/rpc.py` - `forceexit`, `stop`/`stopentry` (состояние бота STOPPED не открывает новые входы, `process_stopped`), `emergency_exit` для безвыходных ситуаций; стоп-лосс на бирже (`stoploss_on_exchange`, `handle_stoploss_on_exchange`, перевыставление и trailing) - защита сохраняется при падении бота; предупреждения о ликвидации (`check_liquidation_warnings`).

Защита от lookahead: есть встроенные команды `lookahead-analysis` и `recursive-analysis` (`optimize/analysis/`): прогоняют стратегию на усечённых данных и сравнивают сигналы, чтобы поймать использование будущих свечей и нестабильность рекурсивных индикаторов. Это про баги стратегии на pandas; параметрической утечки LLM нет по определению. Идея полезна как тест "усечь историю - решение не должно измениться".

Слабые места: синхронный монолит и SQLite/SQLAlchemy; нет идемпотентного клиентского ID; запись в БД после ответа биржи; поток RPC и основной цикл синхронизированы замком; огромный объём кода под множество бирж; GPL. Не про LLM.

Можно взять как идею: protections как набор чистых функций + таблица локов (`state/locks.json`) с причиной и `until`: малая-средняя, высокая; "сначала выходы, потом входы, стоп на бирже, входы только в состоянии RUNNING" - у нас уже по смыслу; стартовая реконсиляция открытых ордеров и позиций с биржи и обработка неизвестных ордеров: средняя, высокая; dry-run как штатный режим того же кода: средняя, высокая; `lookahead-analysis` как тест: малая-средняя, средняя. Нельзя: копировать код (GPL-3.0 заражает проект при распространении), тащить БД-модель и FreqAI.

### 7.4 Что нашёл в коде такого, чего не было видно по сниппетам

- В TradingAgents вообще нет исполнения и жёсткого риска; "risk team" - три LLM-персоны. Зато данные имеют добросовестную point-in-time обрезку, а память - отложенный settlement по альфе.
- ai-hedge-fund сильно изменился: теперь это двухстадийный конвейер с детерминированным риском и хэш-цепным ледгером с kill switch. Это ближайший по духу к нам образец.
- freqtrade не использует client order id, и запись в БД идёт после ответа биржи; реконсиляция - по `fetch_orders` при старте и в особых случаях.

### 7.5 Что тревожит

- Ни один из трёх проектов не защищает от параметрического lookahead и не санитайзит рыночный текст для LLM.
- Нигде нет доказательства прибыли после издержек; в обоих LLM-репозиториях есть disclaimer "не для реальной торговли".
- Ни в TradingAgents, ни в ai-hedge-fund нет реконсиляции с реальной биржей: для live они бесполезны как "готовое", только как источник идей.
- Выводы о кодах получены чтением выборочных файлов (setup.py, portfolio_manager.py, trader.py, structured.py, date_window.py, backtest.py, memory/*, risk/limits.py, pipeline/stages.py, execution.py, clock.py, ledger.py, protections/*, части freqtradebot.py и exchange.py); остальное не читалось.
