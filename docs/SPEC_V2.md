## 0. Честная рамка
- Edge системных правил не найден (`RESEARCH.md`, `BACKLOG.md`), капитал около 39 USDT. v2 не обещает прибыль и не повышает риск. Ценность: (1) дисциплина и защита (исполнитель вне LLM, жёсткие инварианты), (2) реакция «как у скальпера» без простоя (события, свечи, объём, уровни секундами, не минутами чата), (3) измерение гипотез на бумаге и малых деньгах с честной статистикой. Цели вроде «30 -> 100» ориентир, не повод менять лимиты.
- На счёте около 39 USDT минимальные лоты ограничивают лесенки тейков и добор (часто 1-2 части); система обязана говорить об этом заранее (`W_LADDER_COLLAPSE`, `ADD_TOO_SMALL`), а не молча деградировать.
- Скальп означает «мозг заранее пишет условия, исполнитель торгует секундами»; LLM в петле на каждый тик не стоит и не нужна (латентность 2-60 с).

## 1. Принципы и инварианты безопасности
### 1.1 Принцип «план + исполнитель»
Мозг редко и глубоко пишет и обновляет планы (минуты-часы); исполнитель выполняет их в секундной шкале без LLM. Мозг не обходит guard, не знает размера и плеча, не отправляет ордера. Исполнитель не выдумывает сделки: он действует только в рамках принятого плана (вход по его условию, сопровождение по его правилам) и защитных протоколов.

### 1.2 Инварианты (нарушение = дефект уровня «блокирует релиз»; все проверяются тестами `tests/test_invariants_v2.py`)
| # | Инвариант |
|---|---|
| I1 | Любое действие, которое может увеличить риск (вход, добор, постановка входного лимита), проходит `guard.evaluate`/`guard.evaluate_add` В МОМЕНТ отправки (по живой цене), а не только при приёме плана. Размер, плечо и маржа приходят только из guard; в плане их нет. |
| I2 | Позиция всегда под биржевым стопом. Вход атомарен со стопом (встроенный `stopLoss`); порт отказывается создавать вход без стопа; после входа стоп проверяется чтением позиции; нет стопа = немедленная установка, а если невозможно, аварийное закрытие. |
| I3 | Стоп двигается только в сторону уменьшения риска (long: вверх, short: вниз). Расширять и снимать нельзя. Проверяется в четырёх независимых слоях: валидатор плана (статически), движок правил (не создаёт ослабляющих действий), Gate исполнителя (сравнение с ТЕКУЩИМ биржевым стопом), порт/клиент (читает стоп перед записью). Единственное исключение: восстановление потерянной защиты до уровня, который уже был (2.7). |
| I4 | `config/risk_profile.json` и лимиты guard неприкосновенны. `config/exec_limits.json` может только СУЖАТЬ разрешённое, ключей, ослабляющих guard, в нём нет. Лимиты меняет только владелец по прямому указанию. |
| I5 | Без усреднения убытка и без мартингейла. Размер новой сделки не зависит от предыдущих убытков (guard может только уменьшать через лестницу просадки). Добор допустим ТОЛЬКО как пирамидинг прибыльной позиции (1.7), по умолчанию ВЫКЛЮЧЕН. |
| I6 | Идемпотентность: `orderLinkId` детерминирован (`tbx-<план>-<действие>`), намерение пишется в WAL ДО отправки, повтор после неопределённого ответа запрещён без проверки по `link_id`. Команды мозга идемпотентны по `cmd_id`. |
| I7 | Kill switch (`state/KILL`) проверяется первым в каждой точке записи (Gate, обработка команд, цикл), читается с диска каждый раз. При KILL разрешены только снятие ордеров, закрытие и подтягивание стопа; с `flatten` исполнитель закрывает всё. |
| I8 | Неопределённость = не торговать. Устаревшие данные, расхождение с биржей, потеря приватного канала, неизвестный ответ, невалидный конфиг: `hold` (входы и добор запрещены, защитные действия разрешены). |
| I9 | Один писатель на состояние: исполнитель единственный пишет `state/plans/*`, шину, журнал плановых сделок и ордера; мозг пишет только команды в `_inbox` (и прежние `ideas/journal post/session`). Один экземпляр исполнителя (lock). |
| I10 | Все решения (мозга, правил, защит) в append-only журнале решений с причиной, ценой и R на момент, ссылкой на событие и досье (`decisions.jsonl`, хеш-цепочка). Журнал сделок `trades.jsonl` остаётся append-only и совместимым. |
| I11 | Недоверенный текст не попадает в мозг: `brief` и события содержат только числа, перечисления и проверенные идентификаторы; свободный текст третьих лиц отсутствует; ответ мозга принимается только по схеме, непроходящий схему отбрасывается (в торговле нет «достань решение из текста»). |
| I12 | Данные для решений свежие: цена не старше `entry.max_price_age_s`, свеча подтверждена, вход не гонится за ценой (`max_chase_bps`). Бумажные сделки не заглядывают вперёд: время и цену ставит система. |
| I13 | Мозг-пакет (`tb.brain`) не импортирует биржевой код и не читает каталог ключей; ключ Bybit нужен только процессу исполнителя; ключ Anthropic только процессу API-мозга. |
| I14 | Деградация безопасна: падение исполнителя, мозга, WS или REST оставляет позиции под биржевым стопом (и лесенкой тейков); любой возврат к жизни начинается с реконсиляции. |
| I15 | Совместимость: прежние команды и форматы работают параллельно до решения владельца о переключении (6). |
| I16 | Бумажный режим не влияет на живые лимиты, слоты и дневные счётчики. |

### 1.3 Что не меняется
Профиль риска, формулы guard (размер от стопа плюс издержки круга, плечо, ликвидационный зазор, лестница просадки, дневной лимит, серия стопов, сессии, корреляции, `learning`), правила TRADING.md (подтверждение входа, стоп за экстремум, паузы после стопов, разбор сделок), CLAUDE.md. Новые защиты формализуют существующие правила TRADING.md и только ужесточают.

### 1.4 Защита стопа в глубину (инвариант I3)
1. `plan_schema.validate_*`: `E_STOP_WIDEN` при `amend`, статическая проверка правил (`move_stop.to=price`).
2. `logic/rules`: действие `move_stop`/`trail` создаётся только если новый стоп строго строже `cur_stop` (иначе `NOT_TIGHTER`, без действия).
3. `executor/gate`: сравнение с биржевым стопом (не с копией в плане), минимальный шаг/интервал/зазор, `INVARIANT_VIOLATION` при попытке ослабить.
4. `venues/bybit_exec.set_stop`: читает стоп с биржи, отказывает без вызова API.
Тест-ловушка (обязательный): специально сломанный движок правил выдаёт ослабляющее действие, Gate и порт обязаны его остановить.

### 1.5 Цепочка безопасности входа
План принят (валидатор+guard preview) -> условие входа выполнено (свежие данные) -> Gate: KILL/hold/свежесть/сессия/защиты/`symbol_busy` -> `guard.evaluate` по живой цене (может отказать, план остаётся `armed` с ограниченными повторами) -> `size_mult` (только вниз) -> WAL intent -> ордер со стопом -> проверка защиты -> журнал `open`. Любой шаг может остановить вход; ни один не может его «протолкнуть».

### 1.6 Недоверенные данные
Источники текста, которые НЕ попадают в мозг и не исполняются: названия монет/тикеров вне regex, описания, новости, README/SKILL внешних проектов, поля `idea_note` из сканера, тексты исключений. Строки мозга (`thesis`, `reason`) считаются данными: обрезаются, очищаются от управляющих символов, в `brief` возвращаются только в поле `own_thesis`.

### 1.7 Добор позиции (пирамидинг): РАСШИРЕНИЕ ВОЗМОЖНОСТЕЙ БЕЗ ОСЛАБЛЕНИЯ ЛИМИТОВ. ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ ВЛАДЕЛЬЦА (Q1)
Нынешнее правило: «без усреднения убытка» (`allow_averaging_down=false`, один вход на монету). Это правило ОСТАЁТСЯ. Новая возможность: наращивание уже ПРИБЫЛЬНОЙ позиции плана. По умолчанию выключено: `config/exec_limits.json: pyramid.enabled=false`. Пока владелец не подтвердит и не включит, правило `add` в плане принимается с предупреждением `W_ADD_DISABLED` и пропускается.
Обозначения: `s=+1` (long) / `-1` (short); части позиции `(e_i, q_i)`; `S` текущий биржевой стоп; `R0` риск-бюджет исходного входа по guard (`risk_usdt`, уже включает издержки); `f = fee + slip` (taker, `costs.bybit`); `realized_net` реализованный результат плана с учётом всех уплаченных комиссий.
Худший исход плана при срабатывании текущего стопа:
`W(S) = realized_net + sum_i q_i * s * (S - e_i) - f * S * sum_i q_i`.
Условия добора (ВСЕ обязательны, проверяются Gate в момент отправки, не в плане):
- P1. `pyramid.enabled=true`; правило `add` есть в плане; число добавлений `< pyramid.max_adds` (умолч. 1); план в `managing`, не `hold`, нет KILL.
- P2. Позиция в плюсе не менее `X` R: `pnl_r >= max(X_правила, pyramid.min_r)` (умолч. `pyramid.min_r = 1.0`), по свежей цене; в `when` правила обязательно есть конъюнкт `pnl_r gte x` (статическая проверка `E_ADD_NOT_PROFIT_GATED`).
- P3. Стоп уже в безубытке или лучше: `s*(S - avg_entry) >= 2*f*avg_entry` (цена входа плюс комиссии круга). Иначе отказ `ADD_STOP_NOT_BE`.
- P4. Суммарный риск плана по ВСЕМ частям не превышает исходного бюджета: после добора `W(S_после) >= -R0`. Размер добора: `q_add = floor_step(min(A, B))`, где `A = risk_frac * R0 / loss_unit`, `B = (W(S) + R0) / loss_unit`, `loss_unit = |px - S| + f*(px + S)` (потеря на единицу при срабатывании стопа, включая издержки). Стоп НЕ двигается назад и не расширяется (добор вешается под тот же `S`).
- P5. `guard.evaluate_add`: сессия не истекла и бюджет не исчерпан, `dd_mult > 0`, дневной лимит убытка и серия стопов не достигнуты, суммарная маржа позиции `<= margin_per_trade_max`, плечо не выше потолка, ликвидационный зазор по новой средней цене и стопу, минимальный лот и номинал. Нет нового слота и нового риска сверх резерва `R0` (резерв уже учтён в `risk_usdt` сделки).
- P6. Интервал с предыдущего добора `>= pyramid.min_gap_s`; свежая цена; нет незавершённого действия по плану.
- P7. После исполнения исполнитель пересчитывает `W` по фактическим исполнениям; если `W < -R0` (проскальзывание), немедленно сокращает добавленную часть reduce-only и пишет `INVARIANT_REPAIR`.
Запрещено навсегда: добор при `pnl_r < X`, при стопе хуже безубытка, после закрытия плана, увеличение исходного риска `R0`, добор в монете, где открыт другой план, добор при `hold`. Плечо и маржа не растут сверх потолков профиля; по счёту около 39 USDT добор чаще всего упрётся в `margin_per_trade_max` или минимальный лот (`ADD_TOO_SMALL`) — это нормально и честно сообщается.
Что нужно решить владельцу: (а) принять правило в таком виде или отказаться; (б) значения `min_r` (1.0), `max_adds` (1), `risk_frac` потолок (1.0); (в) включать ли в тестнете сначала. До ответа код пирамидинга пишется и тестируется (WP3, WP5, WP9), но выключен.

### 2.4 День работы (чат-режим)
1. Владелец: «начинаем торговлю». Мозг: `./tb exec status`; нет исполнителя -> просит владельца запустить/запускает `./tb exec run --profile trade` (в фоне); `./tb brief --scope start`; анализ (чат-мозг может ещё искать и считать сам); `./tb session start ...` (как сейчас); `./tb plan submit` по 1-3 планам (скальп, интрадей), часть как `--mode paper` для гипотез; `Monitor ./tb events --follow --consumer chat`.
2. Событие (`entry_filled`, `milestone`, `scanner_signal`, `connectivity`, ...): строка будит мозг -> `./tb brief --scope event` -> решение `plan stop/amend/close/cancel/submit` -> `events ack`.
3. Исполнитель в это время: вход по условию, лесенка, правила BE/трейл/таймаут/инвалидация, события, журнал. Мозг может молчать часами (ноль токенов).
4. «Заканчиваем»: мозг `plan cancel` для armed, `plan close` для открытых (или `exec halt --flatten`), `session stop`, разбор `journal post`, `exp stats`.
API-режим позже: те же шаги, мозг это демон `brain run` с триажом и Messages API; события те же, ack те же.

## 3. Сводка подсистем (подробности в файлах)
- План (01): декларативный JSON `tb.plan/1`: вход (условие `when` из конечного словаря свечей/объёма/цены + способ `how` market/limit/adopt), стоп, лесенка тейков, правила сопровождения (BE, трейл, частичный выход, таймаут, инвалидация, добор, `notify`), срок жизни, риск-множитель (только вниз), теги эксперимента; состояния draft/armed/entered/managing/closed/cancelled/expired/invalidated (+rejected); правила `amend` по статусам; коды валидации E_/W_; два полных примера.
- Исполнитель (02): один демон, синхронное ядро + asyncio-оболочка, цены из WS tickers и свечи из WS kline (`confirm`), REST для подкачки/дыр/записей, Gate с 9 проверками, WAL и `link_id`, реконсиляция по таблице расхождений, защиты, деградация при потере связи, paper-порт тем же кодом.
- Мозг (03): CLI `plan/brief/events/exp`, журнал решений с причинами, шина событий с курсорами delivered/acked, `brief` по белому списку полей, режимы чат/API.
- Оценка гипотез и дашборд (04): теневые планы и варианты, `exp stats` с честными оговорками, дашборд с верхней полосой, доской планов, позициями с правилами, лентой решений, брифингом.

### 4.2 Что заменяем (постепенно)
Ручной цикл «агент сам вызывает `./tb bybit trade open/close/sync`» заменяется планами и исполнителем. Прежние команды остаются как «ручной режим владельца» и аварийный путь (`close`, `cancel`). `cron sync` раз в 15 минут и `watch --pending` заменяются реконсиляцией исполнителя, но не удаляются.
### 4.3 Совместимость журнала и команд
- `trades.jsonl`: ничего не переименовывается; прежний код читает новые файлы (новые события игнорируются `_load`, новые поля необязательны). Режим `paper` уже существует. Плановые сделки идут с `venue=bybit`, как сейчас.
- `./tb bybit trade open ...` работает как раньше (фазы 0-4). В фазе 5 по решению владельца: `open` становится обёрткой над планом (`--via-plan` по умолчанию), `--direct` остаётся для владельца. Пока оба пути живы, защищаемся от двойной записи: прежний `sync` пропускает записи с `plan_id`; прежний `close` для плановой монеты закрывает позицию на бирже и не пишет в журнал (исполнитель финализирует идемпотентно); `symbol_busy` в Gate не даёт плану входить в монету, где есть прежняя позиция/лимит.
- Старые позиции можно взять под управление `plan adopt` (стоп на бирже обязателен).

## 9. Словарь
План: JSON `tb.plan/1`. R: дистанция начального стопа от средней цены входа. `R0`: риск-бюджет сделки по guard. Gate: единая дверь проверок исполнителя. WAL: запись намерения до отправки. Порт: интерфейс биржи (`VenuePort`): live, paper, fake. Hold: запрет рискующих действий при неопределённости. Wake-событие: событие, будящее мозг. Бриф: компактное досье по белому списку полей.
